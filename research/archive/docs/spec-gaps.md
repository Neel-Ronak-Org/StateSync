GAP-1 | Part C1 | C1 Scope / C1 Notes | build agent | 2026-08-14
Does a successful query on the memory-HIT path also write a new trajectory
back via memory.put_trajectory, or only a successful MISS-path (full schema
read) query? "Successful queries write a trajectory back" (C1 Scope) and "The
trajectory write happens only on execution success" (C1 Notes) both read as
general rules, but neither says whether a hit counts. Nothing in A4.8, A6, or
the Verification section (C1-V1..V6) disambiguates this either.
Resolution (decided, not a BD -- implementation-level, reversible): hit-path
successes do NOT write back. Only hit_count on the reused trajectory is
bumped (inside memory.get_trajectory itself). Reasons: (1) a fresh
summarization LLM call on every hit would add tokens/llm_calls to the
treatment run that the control run never pays, partially offsetting the very
reduction C1-V1 measures; (2) repeatedly writing near-duplicate trajectories
for the same recurring query pattern has no stated benefit and works against
Qdrant collection hygiene. See orchestrator/nodes/sql_agent.py module
docstring. Revisit if C1-V1/C1-V2 results suggest hit-quality degrades
without reinforcement.

GAP-2 | Part C2 | A3 / Deliverable 5 (malformed_queries.json) | build agent | 2026-08-14
"join_cardinality" is a valid ErrorCategory (state.py) and Deliverable 5's
fixture requires an mq_10 seed with expected_category="join_cardinality" (a
fan-out join that double-counts SUM(oi.line_value) across a 1:many join to
fulfillments). But this query does not error: it executes successfully
(ok:true, non-empty rows) with silently wrong aggregate values. A3's
classifier is explicitly "deterministic... a mapping from engine error codes
and regex patterns" operating on sqlstate/message/empty_result -- there is no
engine-observable signal that distinguishes a correct join from a fan-out
join. Nothing in A3, A4, or C2 describes a mechanism (row-count sanity check,
cardinality heuristic, or otherwise) for detecting this deterministically.
Resolution: see BD3 (docs/phase_b_amendment.md). mq_10 is retained in the
fixture exactly as specified (the deliverable requires copying its structure
verbatim), but it structurally cannot enter the classifier at all -- the
query succeeds, so no failure/empty-result ever reaches A3. bench_correction.py
and C2-V2 report this seed honestly as "never reached the classifier
(non-erroring, semantically wrong result)", distinct from a 0%-repair-rate
category where the classifier fires but no fix is found.

GAP-3 | Part C2 | Appendix 2.4, mq_08 | build agent | 2026-08-14
The literal mq_08 SQL given in the spec (`ST_DWithin(geom, 'POINT(72.87
19.07)', 5000)`) does not reproduce the intended failure against this
environment's Postgres/PostGIS: the untyped string literal casts cleanly and
the query returns ok:true with a real row, not the described "untyped
literal, missing SRID and geography cast" error. Verified empirically (see
scratchpad of this session) before freezing the fixture.
Resolution: substituted a verified-working spatial_invalid trigger with the
same fault family (a geometry/geography SRID mismatch, still under
A4.5/A5's SRID 4326 contract): `ST_DWithin(geom::geometry,
ST_SetSRID(ST_MakePoint(72.87, 19.07), 3857), 5000)`, which reliably
produces sqlstate XX000 with "Operation on mixed SRID geometries" in the
message (matches the taxonomy's `(?i)geometry|srid|postgis` regex). This is
the same category of mistake (an SRID that doesn't match the column's 4326)
as the original text described, just a concrete query that actually
reproduces it here. Not a BD -- this is a fixture-content correction
(Appendix 2 fixtures are "populated... then frozen" per instructions, not a
Strategy/Build-Level decision), recorded for traceability only.

GAP-4 | Part D | Appendix 2.1, 2.3 | build agent | 2026-08-15
Two pre-existing gaps in Phase B's frozen fixtures, both invisible
until Part D actually pinned the real 'digipin' library: (1) Appendix 2.1
requires locations.digipin values "generated by the pinned library ... at
fixture-build time" -- but the library wasn't pinned yet in Phase B, so
gen_seed_fixture.py used an explicit, self-documented stub encoder instead
("Real values generated by gen_digipin_fixture.py with the pinned library").
(2) Appendix 2.3 requires >= 1 digipin_reference.json pair with >= 3 OTHER
seeded locations within 2km -- but every city in the seed fixture caps at 3
locations total under +-0.05 deg (~5.5km) independent jitter, so a
location's own nearby-within-2km count maxed out at 1 across all 50 seeded
locations (verified empirically), never reaching 3.
Resolution: pinned 'digipin' (real PyPI package, confirmed installable) in
orchestrator/pyproject.toml; replaced both stub encoders with real
encode()/decode() calls; regenerated fixtures/ondc_seed.json (confirmed via
diff that ONLY locations.digipin/lat/lon changed -- same RNG call sequence,
so no other table's rows or FK assignments were touched) with jitter
tightened to +-0.005 deg (~555m half-width, giving a ~1.57km worst-case
diagonal, a deterministic guarantee rather than a probabilistic hope) and
one added hub location (loc_0051, placed at the centroid of an existing
3-location city cluster, appended to the locations list only after every
rng.choice(location_ids) call elsewhere in the generator had already run --
verified via the same diff technique that this, too, changed nothing else).
Regenerated fixtures/digipin_reference.json for real, and fixed a second,
related bug found while doing so: the generator had been freezing the
PRE-ENCODE input coordinates as each pair's lat/lon, but decode() returns
the center of the containing grid cell, not an exact inverse of encode() --
so D-V5's "decode(digipin) matches the frozen coordinates to 6dp" could
never pass by construction against pre-encode values (verified: 0/20 matched
before the fix, ~2m-scale differences each -- consistent with D-V4's own
measured ~2.5m round-trip precision). Fixed to freeze decode(encode(...))'s
own output as the regression baseline, which is what "a mismatch means the
library or config drifted" (D-V5) actually requires. User explicitly
confirmed regenerating the frozen Phase B seed fixture (not just Part D's
own new fixtures) before this work proceeded, given it touches previously
shipped data. Not a BD -- both are fixture-content corrections against the
existing spec text, not new Strategy-level decisions.

GAP-5 | Part E1 | E1 Scope, D7/C2 boundary | build agent | 2026-08-15
E1 Scope says decomposition (D7) splits a hybrid query into a SQL sub-task
and a doc sub-task, but is silent on whether the SQL sub-task engages C2's
correction loop (retry on a classified, retriable failure) the way the pure
sql route does. The spec frames the correction loop consistently as a
sql_agent_node / sql-route concept (C2 Deliverable 2's own language: "not a
try/except retry loop... inside sql_agent_node"); E1 never says it also
covers a decomposed sub-question executed from within the hybrid route.
Resolution: implemented hybrid's SQL sub-task as a simplified single-shot
generation+execution (no memory consultation, no active interrogation, no
correction-loop retry) -- reasoned that a decomposed sub-question is by
construction simpler than a standalone sql-route question (decomposition
already isolated the structured-data part), and that wiring hybrid through
C2's actual graph edges would mean either duplicating sql_agent_node's
correction-loop machinery for a second call site or routing hybrid through
the sql route's own conditional edges, neither of which Deliverable 5's
"Unstructured Knowledge Engine node replacing both stubs" language
suggests. On a sub-task SQL failure, the error is still classified (A3,
same classify_error() sql_agent_node uses) and surfaced honestly via
state.errors rather than silently treated as an empty result -- found as a
real bug during E1-V4 testing (a hallucinated table name was originally
surfacing as "no sellers breached SLA," a fabricated answer, instead of a
reported failure) and fixed before this gap was recorded. Not a BD -- this
is an implementation choice for an unaddressed case, not a reopening of a
locked D-numbered decision.

GAP-6 | Part A | A5 schema fingerprint / A4.1 | build agent | 2026-08-15
A5 defines the fingerprint over "each table in the application schema" and
lists what it excludes (indexes, comments, row counts, sequence values,
schema_versions) -- but never says what "the application schema" means when a
Postgres EXTENSION installs its own table into the same namespace. PostGIS
creates spatial_ref_sys in `public`, so both A4.1's schema.list_tables and A5's
fingerprint query (`information_schema.tables WHERE table_schema='public' AND
table_type='BASE TABLE'`) surface it alongside the 12 real A5 tables.
Verified empirically under BOTH statesync_migrator and statesync_reader: 14
base tables in public = 12 A5 application tables + schema_versions +
spatial_ref_sys. So `mcp/fingerprint.py` IS currently hashing spatial_ref_sys's
columns into the A5 fingerprint.
Resolution (partial, deliberately): FIXED on the A4.1 side only.
schema.list_tables now excludes extension-owned tables (pg_depend deptype 'e'
-- ownership, not a name denylist), which stops the SchemaRetriever from
spending a describe_table call on spatial_ref_sys for every miss-path query on
both the control and treatment arms. list_tables now returns exactly the 12 A5
application tables. NOT FIXED on the fingerprint side, and not silently
absorbed either: changing the fingerprint formula changes the fingerprint
value, which under D4's validate-on-read invalidates every stored trajectory
and requires re-stamping schema_versions -- that is a decision about D4's
blast radius, not a cleanup, so it is flagged here per A0.1 rather than made.
Note the practical impact today is nil: spatial_ref_sys's shape is fixed by the
PostGIS version, so the fingerprint is stable; it would only move on a PostGIS
upgrade, and invalidating trajectories on a PostGIS upgrade is arguably the
conservative behavior anyway. Escalated for the team to decide.
(The Agent Task Packet's Task 5 predicted the opposite -- "the fingerprint
already excludes system tables by operating on the application schema" -- and
instructed STOP if the fingerprint changed. It did not change, because Task 5's
edit touches only schema_tools.py's own separate query; the packet's premise
about fingerprint.py is what turned out to be wrong. Also recording that the
packet's expected count of 17 application tables does not match this schema:
the live count is 12.)

NOTE-1 (not a gap) | Appendix 3 | flags.memory.enabled default | build agent | 2026-08-15
Recording a shipped feature-flag DEFAULT change, which flags.toml's own header
says is explicitly not a BD ("Changing the *existence* of a flag ... does
require a BD entry" -- changing a default does not). Logged here only so the
change is traceable rather than silent.
`memory.enabled` default flipped true -> false. On the local model,
memory-on measurably regresses M2 (C1-V3: treatment mean distinct-result-sets
1.5 vs control 1.0) and drops the verify_b golden rate from ~10/10 to 7/10 --
the hit path's compact insight is less reliable than the miss path's full
schema read. See BD6 (docs/phase_b_amendment.md) for the recorded disposition
of the underlying cause.
This changes only the SHIPPED DEFAULT. The flag remains a first-class D13
control: bench_memory.py and check_consistency.py both set it explicitly per
run, so C1-V1/C1-V3's A/B is unaffected, and flags_snapshot still captures it
at query entry (A2). Reversible by editing one line; the re-baseline runbook
(docs/rebaseline_runbook.md, step 4) re-decides it on the graded model.

GAP-7 | Part F | F-V2 over-exposure experiment | build agent | 2026-08-15
F-V2 asks for the over-exposure experiment to run "at surfaces of 9, 15, 25,
and 40 tools by registering inert decoys" -- numbers that exactly match
mcp.tool_ceiling's own scale (9 = the current registered tool count, 15 = the
configured ceiling, Appendix 1). But F-V2 itself, and M9, measure SUPERVISOR
ROUTING accuracy ("the Supervisor routes a fixed query set to the correct
specialist"), and D1 deliberately decoupled the Supervisor's 3-route
classification from MCP's tool list entirely: orchestrator/nodes/
supervisor.py's system prompt never names a single MCP tool
(schema.list_tables, data.run_select, etc.), and the Supervisor never calls
or sees mcp/main.py's _REGISTERED_TOOLS. There is no code path by which
registering decoy MCP JSON-RPC methods could move what the Supervisor's LLM
call sees or how it routes -- the two "tool surfaces" the spec's own
vocabulary conflates are, in this D1-reduced architecture, mechanically
unconnected. (This vocabulary clash traces back further: Strategy Document
§4.2/§7 borrow "tool surface crowds routing accuracy" language from the
original six-agent design MCP-architecture research, written before D1
collapsed Supervisor/Geocoding/COLA into a 3-route classifier decoupled from
MCP's own tool list.)
Resolution: scripts/experiment_tool_ceiling.py interprets "surfaces of
9/15/25/40" as the total number of CAPABILITY DESCRIPTIONS injected into the
Supervisor's own classification prompt (3 real routes + N decoys), reusing
the spec's own scale as decoy-count targets -- this is the only surface that
can actually move M9, and it reproduces the intended phenomenon (a
classification decision degrading as its own context crowds) even though the
numbers no longer literally equal MCP's registered tool count. Decoy
descriptions are drawn partly from Strategy §6's own deferred-scope items
(several -- "geocoding" chief among them -- were literally rejected as peer
routing destinations by D1, a fitting source) plus invented but plausible
logistics-analytics specialist names; none are ever a valid classification
target (_extract_route only accepts sql/docs/hybrid). Not a BD -- this is an
implementation choice for an unaddressed case (A0.1), not a reopening of D1's
own settled reduction.

GAP-8 | Part F | F1 Scope, evaluator pipeline | build agent | 2026-08-15
F1 Scope says the evaluator pipeline "runs the full golden set on a schedule
and on demand" but never defines "the full golden set" -- by Part F the repo
holds seven distinct golden fixtures (phase_b/c1/c2/d_multilingual/d_spatial/
e1/e2.json), each built for a different phase's own Verification section, not
for a continuous evaluation pipeline. Running all seven on every scheduled
tick (golden_run_schedule_cron = hourly) would mean re-running C1's
memory-flag A/B machinery, D's normalization A/B, and E1's LLM-judge
faithfulness scoring on a cron -- none of which the evaluator's own Scorer
registry (SpecScorer, ExecutionScorer) can even score, since those fixtures
don't carry reference_spec or ground_truth_sql/expected_row_count in the
shape those two scorers need.
Resolution: "the full golden set" is defined as the union of the two
fixtures whose shape matches the two ENABLED scorers -- fixtures/golden/
phase_c2.json (ground_truth_sql, for ExecutionScorer) and fixtures/golden/
phase_e2.json (reference_spec, for SpecScorer) -- named in config
(evaluation.spec_scorer_fixture / execution_scorer_fixture), not hardcoded.
Every other phase's golden set keeps its own Verification-section role
(B-V1, C1-V1..V6, D-V1..V7, E1-V1..V8) and is re-run there, and again at
F-V3, unchanged (F2 Notes: "reuses its original Part's procedure unchanged").
Not a BD -- this is an implementation choice for an unaddressed case, not a
new Strategy-level decision; the Scorer registry seam itself (A8) is
unaffected by which fixture feeds it.
