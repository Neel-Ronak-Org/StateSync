# StateSync: full project audit before the final clean-up

26 October 2026. This audit covers the code, switches, data, documents, scripts, tests, infrastructure and repository
state of branch `v3-phase3-workspaces` at commit `1b0e463`. Nothing was changed while auditing. Every number below
was measured from the repository or the running configuration on this date.

---

## Summary

The teachers are right: the repository holds about three projects at once, and only one of them is what we
present.

1. **The product:** an assistant over a database and documents.
2. **The research:** two papers, the verifier study, the Jev experiments.
3. **The history:** eleven weeks of phases, cycles, audits, abandoned experiments and the earlier e-commerce/ONDC
   product.

None of it is hidden or broken. Tests pass and CI is green. But nothing tells a reader which parts matter, and
much of what they open is not used.

**The five problems that make it look unexplainable**

1. **Two different pipelines.** The app's default settings still run the old pipeline: three LLM calls before
   routing, a router that sees only 20 document titles, and passages in document order. The pipeline we evaluated
   and demo (Jev router, coverage line, relevance order, Jev passage order, entity narrowing, follow-ups) only runs
   in a separate demo copy with its own settings file. They differ on 11 switches. Anyone who reads
   `config/flags.toml` or opens the main app on port 3000 sees the old system.
2. **39 switches, most of them experiments.**
   - 28 in `[pipeline]` and 11 elsewhere.
   - Of the 28 pipeline switches, about 14 control features that are off and were decided against, or were only
     needed for an experiment.
   - Every one of them is a branch in the code that someone can ask about.
3. **Research mixed into the product.**
   - **Scripts:** about 80 of the 115 in `scripts/` are experiment scripts.
   - **Documents:** 192 result files in `docs/eval/`.
   - **Tests:** about 10 test files test experiment scripts, not the app.
   - **Research projects:** `research/verifier/` is a separate study.
4. **Documentation that tells an old story.**
   - 342 tracked files under `docs/`: 78 at the top level, of which 47 are old JSON reports from August.
   - The README describes the August state: the Olist demo, a Groq default, local 7B/14B model results. It sends
     readers to `AGENT_HANDOFF.md`, `V2_STRATEGY.md` and `open_items.md`, which are a month or more out of date.
   - Six overlapping guides exist.
5. **Code comments written for us, not for a reader.**
   - Core files cite internal planning IDs ("Phase C1", "A4.7", "BD10", "T4b", "M1 control arm", "GAP-1"): 48
     references in `sql_agent.py` alone, 44 in `synthesizer.py`.
   - The settings files are 994 lines, 420 of them comments, some of them essays about models we no longer use.

**What to do:** keep one product, the one we demo, as the default. Delete what is off, unused or from earlier
phases. Move the research into one clearly separate place. Replace the documentation with a short, current set.

Before deleting anything, tag the current state, so both papers stay reproducible from the tag.

Section 4 has the plan (about three working days). Section 5 lists the decisions only you can make.

## 2. Findings

### 2.1 Two pipelines in one app

| Switch | App default (`config/flags.toml`) | Demo (`research/paperb/demo/flags_demo.toml`) |
|---|---|---|
| `front_door` (router) | off: normaliser → rewriter → LLM router seeing 20 titles | `jev_choice`: one Jev choice question |
| `passage_order` | `document` (the first 8 by document order) | `relevance` |
| `passage_titles`, `rerank_titles` | off | on |
| `passage_rerank` | off | `jev` |
| `hybrid_entities` | off | on |
| `context_carry` | off | on |
| `plain_failures`, `route_recovery` | off | on |
| `inspect` | off | on |
| `llm.provider` | `groq` | `openai_compat` |

Also in the demo's `statesync_demo.toml`: the coverage line is on, and so is the second Jev option wording.

`graph.py` therefore builds two different graphs. Two copies of the app run side by side: port 3000 on the
defaults with images from 5 October, and port 3090 on the demo settings.

**Why it matters:**
- The first thing a reviewer opens contradicts the demo and the paper.
- Our own measurements say the default is the worse pipeline: FinanceBench end to end was 20.0% correct with the
  defaults, and 52.7–63.3% with these fixes.

## 3. Proposed final scope: one story

> **StateSync answers business questions from a company's database and its documents. It routes each question,
> writes safe read-only SQL or finds the right pages, cites its sources, and shows every step it took.**

| Keep (the product) | Remove from the current tree (stays in git history and the tag) |
|---|---|
| Chat with conversation history | The old router path; the `jev` and `jev_rw` arms |
| Front door: Jev choice routing, LLM fallback, database card with the coverage line, follow-ups | Memory and Qdrant; templates; answer checks; repair loop; self-consistency; query rewrite; column profiles; linked table selection; vision; the evaluator |
| SQL agent: schema, sample rows, write, run, classify, retry; the three-layer gate | BM25 hybrid, layout chunker, dataset scope, abstention (measured and left off) |
| Documents: two-round dense search, bge re-ranking with titles, Jev passage order, relevance window, entity narrowing | ONDC profile, DIGIPIN, the `public` dataset and its fixtures |
| Answer writer with code-built citations, figure grounding, evidence tier, "How I got this", plain failures, route recovery | Unused LLM adapters (keep `openai_compat`; optionally `ollama` for offline) |
| Workspaces (business, knowledge, documents, schema), library (uploads), connect your own Postgres | Old phase scripts, reports, cycles, audits, plans, phase logs |
| Pipeline Inspector and Schema tab | Leftover worktrees, merged branches, side containers no longer used |
| Security: tokens, cookie sign-in, rate limit, audit log, row-level security | Experiment switches and their settings keys |

**Decided by you:**
- Dashboards with Build with AI and the `live` simulator.
- The `olist` dataset.
- Multilingual questions.

**Research:** move it under one folder, `research/`, with one subfolder per study: `paper_a/`, `paper_b/`,
`verifier/`. Each holds its scripts, result files, protocols and paper source. The product folders then contain
only the product.

## 5. Decisions only you can make

1. **Dashboards, Build with AI and the `live` simulator:** keep (it's a working, visual feature), or remove to
   keep the project focused on question answering? My recommendation: keep dashboards and pinning, but only if
   you will show them; otherwise remove the simulator and `live` data too.
2. **The `olist` dataset (1.5 million real rows):** keep as a second example database, or remove? Recommendation:
   remove; the SEC database is the one we explain.
3. **Multilingual questions:** remove (recommended; it only exists in the old router path), or rebuild it into
   the front door?
4. **Where the research lives:** a `research/` folder in this repository (recommended; one place, clearly
   labelled), or a separate repository?
5. **What to submit:** the `main` branch after the clean-up (recommended), with the tags for the papers.
6. **The model provider for the final version:** `openai_compat` only (recommended), or also keep `ollama` so
   the app can run offline with a local model?

Answer these and I will start with phase 0 and work through the plan, committing each phase separately so any
step can be undone.
