### F-003-1 The faithfulness judge is never shown the SQL rows the system saw, and is told the document chunks are "what the system actually saw"

- **Class:** 2 (a metric measures something other than its name) · 6 · 10
- **Rank:** `PUBLISHABLE`
- **Bucket:** `DEFECT`

`docs/AGENT_HANDOFF.md` §7 directs cycle 003 at this half and quotes its two
numbers. `V2_STRATEGY.md` §3a publishes `faithfulness | 0.8125` as one of the
four things "genuinely wrong" with the unstructured half. That number is
computed by an instrument that hides half the evidence from its own judge.

`bench_grounding.py:121-130` builds the judge's user message from
`r["retrievals"]` only, under the header **"Retrieved passages (what the system
actually saw)"**. For a `hybrid` query the synthesizer also saw the SQL result
set — `synthesizer.py:398-421` concatenates an SQL context block and a document

The SQL rows are present in the trace the harness reads from, and the harness

### F-003-2 The "independent reference" the judge checks facts against contains a row **count**, not the answer — and three demonstrably true claims were scored factually incorrect

- **Class:** 2 · 7 (the ground truth handed to the instrument is wrong) · 6
- **Rank:** `PUBLISHABLE`
- **Bucket:** `DEFECT`

`fixtures/rubrics/faithfulness.json` instructs the judge to score
`factually_correct` by asking "does this claim match the independent reference
in (4)". `_build_reference()` constructs (4). For any query carrying a
`ground_truth_sql` it appends **`bench_grounding.py:153-154`**:

```python
parts.append(f"Database ground truth (SQL: {q['ground_truth_sql']}): "
             f"row_count={q.get('expected_row_count')}")
```

It never executes the SQL. `expected_row_count` is the number of **rows** the
reference query returns — and every one of these is an aggregate returning a
single row. So the reference handed to the judge for all five hybrid queries
reads, verbatim:

**Transcript**

```
$ python3 -   # reconstruct _build_reference()'s appended line per query
[e1_hybrid_002]
  Database ground truth (SQL: SELECT COUNT(*) FROM disputes d JOIN orders o
  ON d.order_id = o.order_id WHERE o.seller_id = 'S014'): row_count=1
[e1_hybrid_003]
  Database ground truth (SQL: SELECT contracted_sla_hours FROM sellers
  WHERE seller_id = 'S005'): row_count=1
[e1_hybrid_004]
  Database ground truth (SQL: SELECT COUNT(*) FROM orders WHERE seller_id = 'S001'): row_count=1
[e1_hybrid_005]
  Database ground truth (SQL: SELECT COUNT(*) FROM fulfillments WHERE provider_id = 'LP001'): row_count=1
[e1_hybrid_008]
  Database ground truth (SQL: SELECT COUNT(*) FROM orders WHERE seller_id = 'S025'): row_count=1
```

`row_count=1` for every one. The judge read `1` as the answer and marked the
system wrong:

```
$ python3 -   # the judge's per-claim verdicts
[e1_hybrid_002] "Seller S014 has had a total of 2 disputes."  factually_correct=False
[e1_hybrid_004] "Seller S001 has placed 17 orders."           factually_correct=False
[e1_hybrid_008] "Seller S025 has placed 11 orders."           factually_correct=False

$ psql   # the same three, against the live corpus
S014 disputes -> 2      S001 orders -> 17      S025 orders -> 11
```

All three claims are exactly correct. All three were scored factually incorrect
by an instrument that was handed the string `row_count=1` and told it was the
ground truth. This is the `d8a8a86` / `phase_c2` shape — a defective reference
producing confident wrong verdicts — except that here the reference is
**synthesised at run time by the harness**, so no fixture audit could ever have
found it. Audit 001 and 002 both verified fixture ground truths line by line;
neither could have seen this, because it is not in a fixture.

**Does not establish:** this does **not** move `mean_faithfulness`.
`faithfulness_score` is the fraction of claims with
`grounded_in_retrieved_context = true` — `factually_correct` does not enter it,
by design and correctly, per E1-V3's "an ungrounded claim is a failure
regardless of whether it is factually true". It **does** feed
`ungrounded_but_true_count`, which is F-003-3. It does **not** establish that
the fixture's `expected_row_count` values are wrong — they are right, and
correctly named; the defect is the harness treating a row count as a value. It
does not establish what a correct reference would change, because I did not
re-run the judge. And I verified the four DB values **today**, not on
2026-08-15 when the report was written; they match exactly, which is evidence
the seeded corpus is stable, but it is not proof it was identical then.

### F-003-3 `total_ungrounded_but_true` — the quantity E1-V3 singles out as its most informative failure mode — is copied from the judge's free-text field and is **double** what the judge's own per-claim verdicts say

`_judge_query` takes it from a top-level field the judge emits
(`bench_grounding.py:140`, `int(parsed.get("ungrounded_but_true_count", 0))`)

### F-003-4 "Context precision" is computed over **cited** chunks, not retrieved context, and is capped by `citation_max_chunks`; 7 of 8 doc queries sit exactly at a structural ceiling of 0.667 with **perfect recall**

- **Class:** 2 · 6 (a conclusion wider than its measurement)
- **Rank:** `PUBLISHABLE`
- **Bucket:** `DEFECT` in the metric's published gloss and in the undisclosed ceiling.

`V2_STRATEGY.md:203` publishes the interpretation:

> | context precision | **0.622** — ~38% of retrieved context is irrelevant |

`_context_precision` (`bench_grounding.py:102-109`) divides by
`len(cited_chunk_ids)` — the citation list, which `build_citations` caps at
`citation_max_chunks = 3` (`config/statesync.toml:77`). Every scored fixture
entry lists exactly **2** `expected_chunk_ids`. So a doc query that cites the
maximum 3 has a per-query ceiling of **2/3 = 0.667**, and cannot report a better
retrieval however good retrieval is:

**Transcript**

```
$ python3 -   # per query: retrieved, cited, expected, published precision
id               n_retrieved  n_cited  n_expected  precision   prec_over_retrieved
e1_doc_001                16        3           2      0.667                 0.125
e1_doc_002                14        3           2      0.667                 0.143
e1_doc_003                12        3           2      0.667                 0.167
e1_doc_004                14        3           2        0.0                 0.143
e1_doc_005                14        3           2      0.667                 0.143
e1_doc_006                14        3           2      0.667                 0.143
e1_doc_007                14        3           2      0.667                 0.143
e1_doc_008                14        3           2      0.667                 0.143
e1_hybrid_002 .. 008     2-14      2-3           2   0.0-1.0             0.0-1.0

total chunks RETRIEVED across the 16: 156   total CITED: 43

max attainable mean_context_precision on this run (n=15): 0.7778
published                                                : 0.6222
doc-route per-query ceiling (2 expected / citation_max_chunks=3): 0.6667
doc queries sitting EXACTLY at that ceiling                     : 7/8
doc queries with recall 1.0 (both expected chunks retrieved)    : 7/8
```

Three things follow, and all three contradict the published gloss.

1. **The denominator is wrong for the claim made.** 0.622 is computed over the
   43 chunks that were *cited*. Over the 156 that were actually *retrieved and
   put in front of the model*, the same computation gives **0.3639** — so if the
   sentence "~38% of retrieved context is irrelevant" were made about retrieved
   context, the figure would be ~64%, not ~38%.
2. **1.0 is unreachable.** Given the citation counts this run produced, the
   maximum attainable mean was **0.778**. Nothing in `V2_STRATEGY.md`,
   `metrics-report.md`, `limitations.md` or the report states that.
3. **It reads as a retrieval failure and is largely a ceiling.** On 7 of the 8
   doc queries retrieval found **both** expected chunks — recall 1.0 — and the
   metric reports 0.667 because a third chunk was also cited.

Separately, E1-V3's specification of the metric is *"are the expected `chunk_id`s
retrieved **and ranked above noise**"*. `_context_precision` is a set
intersection; rank is never read. The ranking half of the specified metric is
not computed at all.

**Does not establish:** this does **not** establish that the extra cited chunk is
relevant, or that retrieval is good. I spot-read the extras and several are
plainly off-target — `e1_doc_001` cites a *different* supplier's agreement
(`S001` on an `S014` question) — so a real precision penalty exists and the
metric is not merely measuring its own cap. It does **not** establish that 0.622
should be restated as some other number: `min(expected, cited)/cited` is one
defensible normalisation and there are others, and choosing one after seeing the
result is exactly the goalpost-move this repo prohibits. It does not touch
`mean_context_recall = 0.80`, which has no such ceiling and which I reproduced
as published. And `e1_doc_004`/`e1_hybrid_005`'s genuine 0.0 scores are a real
retrieval failure, already root-caused in `phase_e1_log.md`, not an artifact —
I verified the ground truth is right (below, class 7).

Three gaps that compound. The SQL side has `test_scorer_semantics.py` and
`test_scorer_copies_identical.py`; `_context_precision` and the rubric have
nothing. `verify_fv3.sh:100` runs `run_step "E1-V3 (M6)" python3
scripts/bench_grounding.py` and `run_step` records PASS on exit code — so
`E1-V3 (M6) PASS` in an F-V3 summary means the script ran, not that anything
about M6 held. And a judge parse failure returns `faithfulness_score: 0.0`
(`bench_grounding.py:144`) which is then averaged in as a genuine zero, so an
instrument failure is indistinguishable from an unfaithful answer in the mean.

**Does not establish:** this does **not** show any published number is wrong on
this account. I checked, and the published run has **zero** parse failures and
zero query errors — `n with parse_failed: 0`, all 16 scored — so nothing in
`0.8125` is a disguised instrument failure today. E1-V3 sets **no threshold**
by design ("the Strategy Document sets no threshold"), so "PASS = exit 0" is
defensible for the threshold half of the condition; what is unchecked is the
`must enforce` half. It does **not** establish that the enforcement is actually
missing — `faithfulness_score` is the fraction of claims grounded, so an
ungrounded-but-true claim does correctly lower it, and I verified that by
reading the code. The defect is that this is asserted nowhere, which is why it is
`BACKLOG` and not this-cycle work — and why F-003-1 through F-003-4 survived
three cycles.

## Not reached

  I did not re-run `bench_grounding.py`, so **none of F-003-1 through F-003-4
  has been confirmed by a corrected measurement** — they are established as

  have measured nothing about judge variance beyond the two committed runs
