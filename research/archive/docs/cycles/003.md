## 1. What the audit contradicted in the previous briefings

**The gap is one sentence: every previous cycle diagnosed the RAG half's
weakness as SCALE. It is INSTRUMENTATION.**

`docs/cycles/000.md` §3.2, the origin of the belief every later cycle inherited:

> **The RAG half has essentially no evaluation.** M6 context precision 0.622 is
> over 18 documents and 36 chunks. **At that scale the number is close to
> uninformative**, and I did not improve on it.

That is a claim about the *corpus*. Cycle 001 did not touch the half at all —
the string "unstructured" does not occur in `docs/cycles/001.md`. Cycle 002 §1
carried the same framing forward as a coverage debt:

> **Three cycles have now skipped the same half of the product.** … That is §7's
> "shared blind spot" with three cycles of evidence, and it is named here so
> cycle 003 inherits it as a debt rather than a gap.

Both are right that nobody looked. Both are wrong about what was there to find.
The audit opened the instrument and found **three of the four published M6
components are wrong for reasons that have nothing to do with corpus size**:

| published | what it actually is |
|---|---|
| faithfulness **0.8125** | the judge is never shown the SQL rows the synthesizer saw, and is told the doc chunks are "what the system actually saw". 5 of the 6 ungrounded claims are SQL-derived; 4 are single values I verified exactly correct against the corpus. Doc half **1.0000** in both committed runs, hybrid half **0.6250** (F-003-1) |
| ungrounded-but-true **4** | an unvalidated integer copied from the judge's free-text field. Recomputed from the judge's own per-claim verdicts: **2** (F-003-3) |
| context precision **0.622** — *"~38% of retrieved context is irrelevant"* | computed over **cited** chunks (43), capped at `citation_max_chunks=3`. Doc-route ceiling is **0.667** and 7 of 8 doc queries sit exactly on it **with recall 1.0**. Over the 156 chunks actually retrieved the same computation is **0.364** (F-003-4) |
| context recall **0.80** | reproduces exactly. No defect found. |

Plus a fourth, which no fixture audit could have caught because the defective
ground truth is synthesised at run time rather than stored: `_build_reference()`
hands the judge the literal string `row_count=1` as the "database ground truth"
for every hybrid query, and three demonstrably true claims — S014 = 2 disputes,
S001 = 17 orders, S025 = 11 orders — were scored **factually incorrect** against
it (F-003-2).

**Why this matters more than a wrong number.** `V2_STRATEGY.md` §3a's proposal
for this half — and the obvious reading of the owner's cycle-003 direction — is
to make the corpus real by ingesting `olist.order_reviews`' 41,755 free-text
reviews, *"1,160× the current chunk count, already loaded, already checksummed."*
Every one of the four defects above is **independent of corpus size**. Ingesting
1,160× more text first would produce a bigger, more expensive, equally wrong
number, and would make the instrument repair harder to attribute afterwards.
Cycle 000 §3.2 said the number was uninformative because the corpus is small.
It is uninformative because the instrument is broken, and growing the corpus
does not fix it.

**One more thing neither briefing contains.** `V2_STRATEGY.md` §3a defends the
half with *"'no tests' is wrong: … M6 in `scripts/bench_grounding.py`, which
DOES include a hallucination check."* It does. On hybrid queries that check
systematically labels the system's own correct, computed SQL facts as
hallucinations, and its factual-correctness half is fed a row count. Present in
form; measuring something else on half its queries.

## 2. The plan

**Shape: make the instrument trustworthy before making the corpus big — and
never by moving a number.**

The binding rule here is the hardest one in the repo: *never alter a
verification, fixture or scorer to make a number look better.* Three of the four
defects are unambiguous bugs and are simply fixed. **One is not**, and it is
handled by this repo's own established precedent rather than by my judgement.

**The contested one.** Fixing F-003-1 — giving the judge the SQL rows — will
raise faithfulness. My hand-regrade of the four DB-verified claims puts it at
`0.9375` against a published `0.8125`. Changing a scorer's inputs in a direction
that raises the number is exactly the shape of the prohibited act, and I am not
going to argue my way around it. There is also a defensible reading in which
E1-V3 deliberately measures *document* groundedness only — the rubric does say
"document passage" — and no document anywhere records that intent, so §4.2 does
not let me call it a TRADEOFF either.

So it is resolved the way this repo has resolved it twice before:

> `limitations.md`: **"The scorer was NOT changed.** Loosening it after seeing
> the results, to raise M4, would be editing the instrument to fit the number."
> `AGENT_HANDOFF.md` §8: *"a third scorer was added alongside it instead."*
> Cycle 000: the corrected fixture was **a new file**; the original was never
> edited.

**`faithfulness_score` is not touched, and 0.8125 stays published.** A second
measure is added *alongside* it, under its own name and its own rubric file,
with both numbers reported and the gap between them explained. `faithfulness.json`
stays byte-identical. Same treatment for context precision: the published
definition is preserved and the over-retrieved figure is reported next to it.

The other three are bugs with no second reading and are fixed in place:
`row_count` is not a ground-truth value under any interpretation; a reported
count that contradicts its own evidence is not a definitional choice; and a
denominator of 15 published as 16 is an error.

## 5. Confidence — where I would look if I were auditing me

**5.1 — I have exactly one noise-baseline sample, and it is of the
*unmodified* harness, not the repaired one.** M1's perfect reproduction of
the published run (0.622/0.80/0.8125/4, 16/16 identical answers) is strong
evidence that a single run of the *old* code is close to deterministic on
this fixture. It says nothing about whether M2's numbers — `0.8958`,
`0.875` — would reproduce on a second run of the *repaired* code. The
repaired harness makes twice as many judge calls per query (v1 pass + the
new all-sources pass) and feeds the judge different reference text on 7 of
16 queries; I have no evidence either way on whether that doubles the
variance, halves it, or leaves it unchanged. If I were auditing this cycle,
a second M2-equivalent run is the first thing I'd want, and its absence is
the single biggest gap in this outcome.

**5.2 — I diagnosed one query's faithfulness-delta causally
(`e1_hybrid_006`) and generalised from it.** Eight queries' `faithfulness_score`
changed between M1 and M2. I traced exactly one to ground truth and found a
real, verifiable defect in the old reference. I did not do the same for the
other seven — four moved up (`e1_hybrid_002/003/004/008`), and I have not
independently re-verified each of those against the database the way I did
for `002` (in the audit) and `006` (during this write-up). It is plausible
some of that upward movement is the judge simply being more lenient with a
denser, more informative reference rather than more *correct* — those are
different things, and I only checked the one direction (a wrong credit
becoming a correct rejection), not the other (whether the richer reference
also invites new unearned credit anywhere).

**5.3 — `_recompute_faithfulness_from_claims` was my own addition, not
something the frozen criteria named explicitly.** A5's criterion says the
test suite must demonstrate "(a) an ungrounded-but-true claim lowers
faithfulness_score." Given A4's "scoring expression untouched" constraint,
I could not test that against the live `faithfulness_score` assignment
itself, so I added a parallel cross-check function and tested that instead.
I believe this is a faithful, non-evasive reading of what A5 asked for — it
adds a new report field, changes nothing existing, and is exercised by a
real test — but it was a judgment call made under the frozen criteria's
text rather than something explicitly pre-approved in that text, and I want
that distinction visible rather than papered over by how confidently the
commit message states it.

**5.4 — Only two of the seven hybrid ground-truth-SQL claims were checked
against the live database by hand** (`e1_hybrid_002`, `e1_hybrid_006`); the
other five (`003/004/005/007/008`) were trusted on the strength of A1's
mechanism being correct (it executes the real SQL through the same path the
orchestrator uses) rather than independently re-verified per-claim the way
these two were. I have no specific reason to doubt them — the mechanism is
generic, not query-specific — but "the mechanism is sound" and "I checked
this instance" are different strengths of evidence, and I want the weaker
one named as what it is.

**5.5 — The full 25-query, 32-judge-call pipeline has not been re-run since
the `out_path.relative_to` regression fix (`eac7eec`) landed.** I verified
the fix in isolation (the exact `Path` operations, both the relative and
absolute cases) and confirmed M2's own report data was unaffected by the
crash it fixed, but I did not spend another ~15-20 minutes re-running the
whole harness end-to-end afterward to see the corrected script exit 0 on a
live run. `verify_fv3.sh` would be the natural place this gets exercised
for real, and it wasn't run this cycle (my own gate list was `pytest`,
`verify_deployed`, `verify_seams`, `shipped_flags --self-test` — the same
four audit 002 and I both ran; the full F-V3 sequence, which takes
significantly longer, was not).

**5.6 — The MCP round-trip for `mcp_run_select` assumes every hybrid
`ground_truth_sql` returns a small number of rows.** `_REFERENCE_MAX_ROWS =
20` is generous for the seven queries I looked at (all single-row
aggregates), but I did not enumerate all seven's actual row counts against
the live corpus to confirm none silently truncates. If one does, the judge
would see a `(truncated)` note rather than a wrong answer — a safe failure
mode, not a repeat of F-003-2's silent-wrongness shape — but I did not
verify which, if any, of the seven actually exercises that path.

**5.7 — Green CI (`pytest`, the four gates) was checked after every commit
this cycle, which is more discipline than some previous cycles applied
mid-build, and I want to say plainly why: because A5's tests are pure
functions with no LLM/MCP dependency, running the full suite is nearly free
(0.04-0.07s), so there was no cost-based reason not to. That is a property
of this cycle's particular fix, not a habit I'm claiming credit for beyond
this session — the next agent touching a harness with a slower test suite
should not assume the same cadence is free for them.
