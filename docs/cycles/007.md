## 1. What the audit changes about this plan

Three findings land directly on this cycle's scope and the plan is shaped
around them rather than beside them.

**F-007-1 removes the plan's assumed head start.** `V2_STRATEGY.md` §3b sizes
the work as *"`/query` already accepts `session_id` and threads it to
`MCPSession`, so half the plumbing exists."* It does not. `MCPSession` has no
`session_id` parameter and mints its own uuid4; the frontend has never sent
one; the request field is stored, marked immutable in `StateSyncState`, and
read by nothing. **Session threading is work in this cycle, not inheritance.**
It is small work — one parameter, two call sites, one frontend change — but it
is on the critical path and was budgeted at zero.

**F-007-2 blocks the cross-modal half.** `_run_sql_subtask` passes
`target_schema` to neither `schema_list_tables` nor `retrieve`, so the hybrid
route always queries `public`. §3a's cross-modal conversation is a `docs` turn
followed by a `sql` turn over Olist; on the hybrid route that turn would
silently answer from the 550-row synthetic corpus. Fixing it is ~2 lines and is
a **prerequisite** for any honest cross-modal claim, so it is in scope.

**F-007-10 sets how the result must be reported.** M3 moved 7.5pp between two
runs of an unchanged build, and `config/statesync.toml`'s declared seed reaches
no model. This project has seven metrics quoted to one decimal place on a
single run each. **The multi-turn fixture will not become the eighth**: QM and
IM are measured on two full runs and both are reported, so the number arrives
with its own repeat attached.

## 2. What is being built

**The design is §3b's and is not being redesigned:** contextual query rewriting
placed **before** the supervisor. A follow-up is rewritten into a standalone
question, after which the entire existing pipeline runs unchanged. Not a new
route — routes decide which engine answers, multi-turn is orthogonal state
every route needs.

## 3. Three decisions — (a) and (b)-adjacent scope CONFIRMED BY THE OWNER, 2026-08-24

**(a) History ships WITHOUT auth, and is therefore NOT the audit log.**
§3b says *"Gated on auth. 'Whose history?' is unanswerable without identity,
which fixes the order: auth → history → everything else"*, and *"session state,
history, and the audit log are ONE table."* Auth is Workstream C1 and building
it in the same cycle as multi-turn does not fit. So `conversation_turns` is
scoped by `(tenant_id, session_id)` only, and this cycle **does not claim the
audit-log deliverable**. The table is designed so identity is an added column,
not a migration of existing rows.

> **✔ OWNER DECISION, 2026-08-24.** Asked explicitly, because this reverses a
> sequence the owner has on record (§3b: *"auth → history → everything else"*).
> Answer: **ship history without auth.** The audit-log deliverable is therefore
> NOT claimed this cycle, and a session-scoped table must not be reported as a
> compliance record anywhere. Auth remains Workstream C1, unstarted.

**(b) The §3b OPEN QUESTION on resume/staleness is side-stepped, not answered.**
§3b says decide it before history ships. This cycle ships history **without a
resume path**: nothing in the UI reopens an old conversation, so no stored
answer is ever redisplayed. `computed_at` is stored from day one so the choice
stays open. The question stays open and is not silently resolved.

**(c) The unwired seed (F-007-10) is NOT fixed this cycle.** Sending a seed
where none was sent is a change that could move every existing metric, and
doing it in the same cycle as the multi-turn build is two variables in one run
— §6 rule 1. It goes to `open_items.md` with the before/after pairing it would
need. Variance is handled here by running twice instead.

> **✔ OWNER DECISION, 2026-08-24.** The two-run requirement in C5 was put to the
> owner with its cost (~90 min for both, an estimate to be discounted given I
> was wrong by 3.5× on M3 the same day) and the alternative of one run with a
> disclosed caveat. Answer: **two runs, full fixture.** C5 and C10 stand as
> written.

## 3a. Considered and deliberately NOT made a criterion — latency

A rewrite adds one LLM call before the supervisor on **every** turn, including
single-turn traffic. On the local 7B that is roughly +15-20s per query. This was
put to the owner before the freeze alongside the offer to add a latency
criterion while one could still be added.

> **✔ OWNER DECISION, 2026-08-24: freeze without it** — *"if needed we can add
> that factor later."*

Recorded precisely, because §4.4 means "later" has a specific shape: once the
criteria are frozen a new criterion **cannot** be added to the block. Latency
can be measured, reported in §5, and carried to `open_items.md` — it cannot
become an acceptance condition for cycle 007. The build will therefore measure
and report per-turn latency before/after regardless (C12 requires any moved
metric to carry its before value, and this one will move), but no criterion
gates on it and none can be added to gate on it.

## Acceptance criteria — cycle 007

Frozen before any code is written. If the build proves one wrong, append a
DEVIATION; do not edit the criterion (§4.4).

**C1 — Session identity is real end to end.**
A `POST /query` carrying `session_id: S` results in an MCP request whose
`X-Session-ID` header is `S`, demonstrated by a captured request, not by
reading code. The frontend sends a stable `session_id` across at least three
consecutive queries in one browser session, verified in a real browser.

**C2 — History persists and is scoped.**
`migrations/010` creates `conversation_turns`. After a 3-turn conversation,
the table holds exactly 3 rows for that `(tenant_id, session_id)` and 0 rows
for any other session id. Reversibility demonstrated live: a `DELETE` for one
session removes exactly that session's rows and nothing else.

**C3 — The rewriter is inert on turn 1 and on context-free questions.**
For every turn-1 question in the fixture, and for every turn explicitly
labelled `needs_context: false`, the rewritten question is **byte-identical**
to the normalized question. This is D-V3's property applied to the rewriter and
it must be 100%, not a majority.

**C4 — The existing pipeline is unchanged for single-turn traffic.**
`phase_c2_v2` (n=25) standard EX is re-measured before and after the build on
the shipped configuration. It does not fall. The published value is 60.0%;
the pre-measurement taken this cycle is the baseline, not that number.

**C5 — QM and IM are both reported, from two runs.**
`docs/bench_multiturn_report*.json` contains QM, IM, reference-resolution rate,
error-propagation rate, rewrite fidelity and guess-rate, each with
`flag_provenance`, **for two complete runs of the same build**. Both runs'
figures are published. No QM figure appears anywhere — report, handoff,
commit message — without its IM beside it and its rewrite fidelity beside that.

**C6 — Rewrite fidelity is measured independently of turn accuracy.**
Every rewritten question is scored for intent preservation against the
fixture's own recorded intent, by a procedure that does not consult whether the
turn's SQL was correct. A rewrite that produces a well-formed question
answering something nobody asked scores as a fidelity failure even when its
turn scores QM-correct.

**C7 — The guess-rate is recorded, because clarification was cut.**
Every turn the rewriter resolved without sufficient context is flagged at
runtime and counted. The report states the guess-rate and, for the guessed
turns, how many were nonetheless QM-correct. Shipping silent guessing
unrecorded is the one thing §3's cut-line forbids.

**C8 — The cross-modal case is reported, not omitted.**
At least one fixture conversation is `docs` turn → `sql` turn with the SQL
turn's correctness dependent on a value from the document turn. Its result is
published whether it passes or fails. If it fails, it is reported as
measured-and-failing with the error attributed by route (§3a's cut-line).
Omitting it from the fixture is not an available outcome.

**C9 — F-007-2 is fixed and shown to be fixed.**
With `schema_retriever.target_schema = "olist"`, a hybrid-route query's SQL
sub-task is demonstrated to query `olist`, by a captured `executed_sql`
naming an `olist` table. The before-state is captured first.

**C10 — The new fixture is audited before it is scored.**
`multi_turn.json` is checked for the defect classes this repo has produced:
zero-row references, no-op predicates (audit 005 F-005-2, audit 006 F-006-4),
and labels nothing checks (audit 002 F-002-7). The defect rate found is
reported whether it is zero or not — that number is the paper claim in §6, and
a fixture audited only after a good score is not evidence.

**C11 — Gates hold.**
seams 26/26 · pytest ≥96/96 · deployed 19/19 · E2 46/46 · tenancy 12/12 ·
M8 40/40, all re-run live at the final commit. M8 is binary; a partial pass is
a fail. Any new table is checked against tenancy before the cycle closes.

**C12 — No regression is absorbed silently.**
Every metric this cycle moves is reported with its before value, including
metrics that got worse and including regressions I cause. If the rewriter
costs single-turn accuracy, that number is published, not traded away.
