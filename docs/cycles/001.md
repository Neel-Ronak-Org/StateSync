## 2. The plan

**Shape: repair the instrument, then use it once on something hard.**

The findings are cheap to close and all of them protect measurements v2 has not
yet made. B2 (the hard fixture) is the item `V2_STRATEGY` §4 says *"must happen
before any number is put in the report"*, it is the direct test of cycle 000's
own largest doubt (§3.3), and it is the second independently-authored fixture
the paper claim in §6 needs for replication. It also runs at
`target_schema = "olist"` — the exact flag F-001-1 leaves unguarded — so the
repair pays off immediately instead of being speculative hygiene.

**Not in this cycle, and why.** Workstream A (multi-turn) is the larger build
and its design is, by cycle 000's own §3.1, the least-validated document in the
repo; it should not be started in the same cycle as an instrument repair.
Workstream C1 (auth) produces no number and is not on the critical path to the
report. B1 (`x`/`x_local`) is **blocked on two owner decisions**, below.

**Deliberately no accuracy threshold on the hard fixture.** A bar set before the
questions exist is an invitation to write questions that clear it. The fixture's
result is whatever it is, reported next to the easy-fixture numbers.

### The two decisions, and how they were settled

**Workstream choice — owner, 2026-08-20: B2, the hard fixture.** The §7 check
the protocol reserves for the owner. Confirmed as planned above.

**F-001-3, the B1 bar — delegated to me by the owner ("take the right call"),
and taken. Recorded in full in `docs/open_items.md`.** The decision, in short:

- The **D-V2 ≥ 81.25% clause is left exactly as written**, and so is the
  English-line clause. D-V2 is the clause that actually rejected migration 005
  and it still separates it from the shipped build cleanly.
- The **D-V1 ≥ 65.0% clause is re-anchored** to a paired pre-measurement on the
  build the fix is applied to. Its absolute anchor came from a build that no
  longer exists, and as of today the clause **fails the rejected migration and
  the shipped product equally** — a criterion that rejects the status quo has no
  discriminating power left.
- **Safety test, which is why this is not the prohibited goalpost-move:** does
  it let migration 005 back in? **No** — 005 fails on D-V2 independently
  (62.5% < 81.25%), so the owner decision in `CYCLE_PROTOCOL.md` §4.3 stands
  untouched. No B1 attempt has been made, so there is no result to dislike;
  what moved was the build, not the goalpost.
- **`da6e49f`'s −10.0pp D-V1 regression is carried as a separate open item**
  rather than dissolved into a lower bar. Re-anchoring releases the obligation
  to recover it, so it is written down instead of forgiven.
- **Per F-001-7**, the English manifestation is **measured and reported** on any
  B1 attempt but is **not** made a gating clause — there is no evidence on which
  to set a bar, and inventing one is how the first bar rotted.

Neither decision changes the criteria below; B1 is not in this cycle's scope.

### A — Instrument repairs (close the audit findings)

**A1 (F-001-1).** `scripts/shipped_flags.py` guards
`schema_retriever.target_schema` exactly as it guards the existing four:
shipped default `"public"`; any other value is a `disk_deviation`, sets

**A2 (F-001-4).** No harness can write a provenance record without naming the
model: a test asserts every `flag_provenance` produced by `require_shipped_flags`
carries an `llm` block with a non-empty `provider` and a non-empty per-role

`docs/AGENT_HANDOFF.md` §6 — state at the point of use that both runs were made

**A4 (F-001-5).** `row_recall` and `mean_row_recall` either compare multisets,

### B — Workstream B2, the hard fixture

**B1. It exists and it is hard.** `fixtures/golden/olist_hard.json`, 15–20
questions over the `olist` corpus, each requiring at least one of: a join across
≥3 tables, a correlated subquery, or a window function. The class each question
exercises is recorded on the question.

**B2. It is built with this audit's own checks designed in**, per
`gen_olist_fixture.py`'s protocol: every question names its expected columns;
every denominator is stated in the question text; every ground truth is executed
against the live corpus before the fixture ships; zero-row references are
rejected; and **no `LIMIT` boundary is left tied** — where a tie exists at the
cut, either the question specifies the tie-break or the question is rewritten.

**B3. Its defect rate is measured and reported, whatever it is.** The fixture is
audited by the same protocol applied to `phase_c2`, and the number of defective
questions found is published — including if it is zero. This is the paper
claim's replication (`V2_STRATEGY` §6), so a clean result is as publishable as a
dirty one.

**B4. It is run paired, on ≥2 providers**, one variable between arms, with
`target_schema = "olist"` recorded in `flag_provenance` by A1 and the model
recorded by A2. Failures are classified with `scripts/attribute_failures.py`.

**B5. The result is published next to the easy-fixture numbers**, with the gap
stated plainly. **No accuracy threshold is set here, deliberately** — a bar
fixed before the questions exist would invite writing questions to clear it. If
the hard fixture scores materially below 88.9%/94.4%, that is the cycle's
headline finding and it is reported as such; if it does not, that is reported
too.

ground truth using a CTE, not a defect in the fixture or an error in the run.

## 5. Confidence — where I would look if I were auditing me

Ranked by how much I would bet against my own work.

**5.1 — The hard fixture's 38.9pp drop is one paired measurement, on one
local-model version and one Gemini per-role configuration.** n=16. It has not
been re-measured on Anthropic, Azure, or a second local model. If I were
auditing this cycle, the first thing I would check is whether the drop
replicates on a different provider pairing — a 38.9pp gap on 16 questions
could in principle be a handful of genuinely hard queries this model class
struggles with specifically (nested-subquery/window-function *syntax*, per the
attribution finding), rather than a general statement about "hard SQL." I
believe the general reading, because BD6 already recorded 2-hop joins as a
measured weakness across four *independent* prior checks — this corroborates
that finding rather than standing alone — but "corroborates" is not
"replicates," and I said so in `metrics-report.md`'s own "does not establish"
line rather than only here.

**5.2 — I judged `oh_j04`'s multi-payment-type attribution NOT a defect, and
I am the same author who missed 12/25 defects in `phase_c2` under similar
reasoning.** The argument (the question doesn't claim exclusivity, so
counting a split-payment order's sellers under every payment type it used is
the natural reading) held up when I re-read it fresh, but "I re-read my own
reasoning and still found it convincing" is exactly the failure mode that
built `phase_c2`. The mitigating fact is that `attribute_failures.py`'s
cross-model check on the actual run found nothing wrong with `oh_j04`
specifically (it scored correct on both providers) — but that is a
correctness check on ONE pair of runs, not an independent audit of the
question's wording the way `oh_wf01`'s defect was caught. If this fixture
gets a second, colder read in a future cycle, `oh_j04` is where I would send
it first.

**5.3 — The three annotated historical multilingual reports are reconstructed
from commit-timestamp evidence, and I am confident in the reconstruction, but
I did not re-run `bench_multilingual.py` to confirm it against a live
orchestrator.** The chain (5a7bb90 / a4293e1 / 4389a01 predate or straddle
`shipped_flags.py`'s introduction at `0711c28`, confirmed by `git show
<sha>:config/flags.toml` at each point, all four boolean flags and all seven
`qwen2.5:7b` role assignments matching the shipped config byte-for-byte at
every one of the three commits) is about as strong as archival evidence gets
in this repo. But it is still archival, not a fresh measurement — I am
treating "the config file at that commit says X" as "the run used X," which
is true only if nothing overrode the file at runtime, and I have no way to
check that for a run that happened before this cycle existed.

**5.4 — `attribute_failures.py`'s CTE-blindness is now known, worked around in
this cycle's write-up, and recorded in `docs/open_items.md` — but the tool
itself is unfixed.** The next fixture that uses a `WITH` clause in its ground
truth will hit the exact same false-positive, and whoever runs it will need to
either remember this finding or read the open item first, because nothing in
the tool itself prevents it from happening again silently. I judged fixing the
regex out of scope for this cycle's *build* — it is a quality-of-life
improvement to a diagnostic tool, not a defect that invalidates a published
number, now that this instance is caught and corrected — but writing this
section is what made me notice I hadn't recorded it anywhere actionable, so I
added the open item rather than ship the gap I was about to just confess to.

**5.5 — B1 (the `x`/`x_local` fix itself) is untouched, as planned, but the
re-anchored acceptance bar has never been exercised against a real attempt.**
The re-anchoring in `open_items.md` is reasoned carefully and I stand behind
the argument, but "the bar is well-designed" and "the bar works when someone
actually tries to clear it" are different claims, and only the second one
matters. The M3 re-run the amended condition makes a precondition of any B1
attempt has not happened — the last M3 measurement is still 2026-08-17.

**5.6 — I did not re-run M8.** I am confident in the reasoning (checked the
import graph directly rather than assuming), but "I checked that the
criterion's conditional wasn't triggered" is a narrower claim than "I
confirmed the adversarial suite still passes." If a future cycle's diff
touches anything closer to the data-plane, M8 should run then regardless of
what triggered it.
