## 1. What the audit contradicted in the previous briefings

**The gap is one sentence: cycle 003 believed it had reported all of its own
regressions. It reported one. There were two, and the second one is still
live — it has a published binary gate reading FAIL.**

`docs/cycles/003.md` §3 records `DEVIATIONS: **None.**` and §4 carries a
paragraph headed *"A regression, self-introduced and self-found"* naming the
`out_path.relative_to(REPO_ROOT)` crash, fixed in `eac7eec`. That is honest and
complete for the regression it knew about. It did not know about the other one.

`56a23bf` (B1) appended a `?v=20260820` cache-buster to the `app.js` script tag
— a legitimate fix for a real caching problem the briefing describes carefully,
*"recorded here so it isn't invisible."* `verify_e2.py`'s E2-V4 check asserts
the literal substring `'<script src="app.js"'`. It broke. `verify_security.sh`
Class 4 delegates to `verify_e2.py` and fails on its exit code, so M8 broke with
it. Published `E2 30/30` is `29/30`; published `M8 40/40` is `39/40`, twice, on
two runs 35 minutes apart.

**Cycle 003 was not careless, and that is the point.** Its gate list — `pytest`,
`verify_deployed`, `verify_seams`, `shipped_flags --self-test` — was run after
*every* commit, and §5.7 explains why that cadence was affordable. §5.5 names
the omission of the longer suites explicitly. The two gates it did not run are
the two that broke, and no re-run trigger anyone had written would have fired:
cycles 001 and 002 both defined the M8 trigger as *"if any data-plane or MCP
code is touched"*, and B1 was frontend-only. **A frontend commit can break the
adversarial security gate while satisfying every stated condition for not
re-running it.** That is the institutional finding, and it outlives this bug.

**Second contradiction, smaller and in the opposite direction.**
`docs/cycles/003.md` §2 states as fact that *"Fixing F-003-1 — giving the judge
the SQL rows — will raise faithfulness"*, and the whole "alongside, not instead"
treatment was designed to guard against a number-raising change. The measurement
was made. It went the **other way**: `mean_faithfulness_all_sources` = 0.875
against a docs-only 0.8958, with the hybrid half −4.2pp. The guard was correct
to apply regardless; its stated premise was wrong, and no published document
says so.

**Third, and the one I would fix first if I could only fix one.** The sealed
briefing is *more accurate than the public record*. `cycles/003.md` §4's
attribution table correctly reads the faithfulness delta as **exceeding** a
zero noise band and attributes it to the A1 repair. `docs/limitations.md` —
which `metrics-report.md` names as "the full account" — attributes the same
delta to run-to-run judge variance, citing "8 of the 16" scores changing when it
is 5, all hybrid, all in the set the repair touched. §5.2 of the briefing itself
says "Eight" and then enumerates five. The correct sentence is sealed; the wrong
one ships.

**What the audit did NOT contradict**, recorded so it is not re-litigated: the
M6 repair itself is sound. I recomputed every published component from the
committed records and they reproduce. `faithfulness.json` is untouched, the
tests are not vacuous, M1 reproduced the published run exactly, and the
`e1_hybrid_006` causal instance holds. Cycle 003's *work* is good; its *account*
of the work has one wrong number, and its *coverage* had a hole shaped exactly
like the two gates nobody runs.

## 2. The plan

**Shape: put the failing gate back to passing by making its check able to fail
for the first time, then make the record match reality.** No new capability, no
corpus growth, no metric moved.

**The one sensitive call, named rather than buried.** A1 alters a verification,
and the number goes up as a result. That is the shape of the act this repo
forbids, so it does not proceed on my judgement — it is put to the owner in §2a
below. The argument for it is that the check is provably wrong in **both**
directions and the replacement is strictly *more* discriminating: the current
assertion has reported `PASS` for months on a page loading four CDN scripts, and
the replacement must be demonstrated to **fail** on a CDN-hosted `app.js`, which
nothing in this repo has ever been able to detect. The number returning to
`30/30` is a consequence of the page genuinely satisfying the property, not of
the bar moving.

**Why not the alternative.** Reverting the `?v=` cache-buster would also restore
both gates and touches no verification. It is rejected: `frontend/nginx.conf`'s
new `Cache-Control: no-cache` only governs *future* stores, so removing the
query string would leave every browser holding a pre-`56a23bf` cached `app.js`
permanently broken — the exact failure cycle 003 hit and fixed. Undoing a real
fix to make a broken check pass is worse than fixing the check.

### 2a. The owner's decisions at plan time — 2026-08-20

Both put before the freeze, both answered, recorded here rather than in
DEVIATIONS because they were decided *before* the build, not discovered wrong
during it (the same treatment `cycles/003.md` §3 gave its two).

**A1's shape — asked because it is the forbidden shape.** Altering a
verification, with the published number going up as a result. Presented with
the case for (the check is wrong in both directions; it has reported `PASS` for
months on a page loading four `cdn.jsdelivr.net` scripts; the replacement must
be demonstrated to *fail* on a CDN-hosted `app.js`, which nothing here has ever
detected) and three alternatives, including reverting the cache-buster and
leaving the gates failing.

> **Decided: "Fix the check, prove it fails harder."** Replace the substring
> match with the two-directional property, demonstrate FAIL on a CDN-hosted
> `app.js` and PASS on the real file, add the assertion to `tests/` so CI holds
> it, and let `30/30` and `40/40` return on their own merits.

So the restoration of both counts is authorised, **conditional on the
demonstration**: if the replacement check cannot be shown failing on a case the
old one passed, it has not earned the number back and A1 is not done. That
condition is in criterion A1 and is the load-bearing half of it.

**The review-corpus ingest.** Presented with F-004-6's specific bearing on it —
review text is short, so 41,755 reviews would leave the chunker exactly as
unexercised as 18 PDFs do, buying scale without buying what scale was meant to
test — and with the option of batching reviews into documents long enough to
exercise the split path.

> **Decided: keep it deferred; do the repair cycle.** It stays the named next
> workstream, now with F-004-6 on the record so it gets *designed* rather than
> just run.
