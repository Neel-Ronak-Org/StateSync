## 1. What the audit contradicted in the previous briefings

**The gap is one sentence: `56a23bf` broke three things. Cycle 004 found two,
fixed them well, and closed the file.**

`docs/cycles/004.md` §1 opens *"cycle 003 believed it had reported all of its
own regressions. It reported one. There were two, and the second one is still
live."* That is exactly right and the same sentence now applies one level up.
The third break is the one that mattered to the **product** rather than to the
record: `56a23bf`'s two new `location` blocks silently dropped all four
security headers, because nginx does not inherit `add_header` into a location
that declares its own. The frontend has served no CSP, X-Frame-Options,
X-Content-Type-Options or Referrer-Policy since. `README.md:234` ticks
Deliverable 8 for "strict CSP headers".

**Cycle 004 named the reason it would miss this, in its own confidence
section, and was right.** §5.7: *"I did not go looking for a third broken gate
beyond the two the audit found… I built against named findings, I did not
re-audit the repo."* That is the correct shape for move 4 and it is not a
criticism. What it means is that the *audit's* coverage bounded the cycle, and
audit 004's coverage of `56a23bf` stopped at the two checks that reported FAIL.
Nothing reported FAIL here, because nothing looks.

**The institutional remedy cycle 004 proposed would not have caught it.**
Amendment §2 concludes: *"The suite's own dependency graph, not a
hand-maintained list of which subsystems are risky, is what should decide when
it runs."* A file-level dependency graph **would** have fired — `verify_e2.py`
reads `frontend/nginx.conf`, so a change to that file would have triggered a
re-run. And `verify_e2.py` would have **passed**, 30/30, because it reads the
config text and the config text is still correct. The problem was never *when*
the check runs. It is *what the check reads*. This is the sharpest correction
this audit makes to the previous briefing, and it is a correction to the
proposed fix, not to the diagnosis.

**Second contradiction: cycle 003 believed its nginx change was purely
additive.** §4 describes the cache fix carefully — *"Fixed two ways… the
verification difficulty this caused is recorded here so it isn't invisible"* —
and §3 records `DEVIATIONS: **None.**` It was a real fix for a real problem and
it cost four security headers, which no briefing in this project has ever
mentioned. `grep -niE "csp|add_header|security header" docs/cycles/*.md`
returns nothing across all five.

**Third: cycle 004's confidence in M8 is placed in a gate that cannot see the
property.** §5.3 weighs *"two M8 runs, both 40/40"* carefully and concludes it
is relying on the fix being narrow and understood. M8 is 40/40 — I re-ran it —
and M8's Class 4 delegates to `verify_e2.py`, which reads the config file. The
one metric the spec defines as binary security cannot observe whether the
deployed app has a security header. That is not a wrong claim in the briefing;
it is confidence resting on an instrument whose reach was never stated.

**Fourth, and smaller: the disclosure cycle 004 wrote to fix a problem
understates that problem.** B2 published, in three documents, *"3 of the 25
references return zero rows and cannot fail… **54.5%** over the 22 that can."*
There is a fourth non-discriminating query by a different mechanism — `c2g_15`,
whose filter matches all 30 sellers — and the shipped 7B's pass on it is
awarded to `WHERE display_name_local IS NOT NULL`, which is not the question.
Over the 21 queries that can discriminate the figure is **52.4%**.

**What the audit did NOT contradict**, recorded so it is not re-litigated:
cycle 004's A1/A2 repair is good work. `tests/test_frontend_asset_checks.py` is
not vacuous — it tests both directions and includes a mutation case the
predecessor provably missed. All six gate counts reproduce at HEAD. The M6
repair from cycle 003 still stands. `phase_c2_v2`'s ground-truth SQL is sound:
24 of 25 row counts match, and the `orders`→`fulfillments` fan-out that would
have corrupted `c2g_02`/`c2g_16` does not exist in this data.

## 2. The plan

**Direction — set by the owner, 2026-08-21, mid-session:** *"choose the
strongest production-path move if you are prompting me with the direction doubt
(I think it is the review ingest, redesigned)."* Their instinct is right and
this cycle takes it, with one thing ahead of it that the audit made
non-optional.

**Shape: two repairs that are small and certain, then the production move.**

**A — deliver the security headers, and check effects instead of specifications.**
F-005-1 is a live product defect: the deployed app claims a CSP it does not
send. The fix to the config is one line repeated and I verified it in a
throwaway container during the audit. The fix that matters is the second half —
**a verification that issues a request and reads the response**, because the
repo currently contains zero of those, and that absence is what let a
five-assertion check pass against a header that was never sent.

**B — disclose `c2g_15`.** The fixture is not edited: F-004-3 routed that class
of fix to the owner and it stays routed, and "do not tune against the fixture
you report from" applies. What is owed is that the published caveat stops
understating itself.

**C — the review ingest, redesigned.** The design matters more than the
ingest, and the audit's measurements dictate it:

- A **raw** ingest of 41,746 commented reviews is the wrong build. Comments
  average **11.9 words** and max out at **45** — against a 512-token chunk
  target. It would leave F-004-6 exactly where it is (the chunker still never
  fires), produce ~41.7k near-duplicate micro-chunks in one vector space, and
  cost ~170 minutes of embedding at the measured 244 ms/embed.
- The redesign is **per-seller review digests**: one document per seller,
  containing that seller's reviews. Measured against the real data, that is
  **2,567 documents**, median 56 words, max 12,426 words, and **246 of them
  exceed 512 words** — so the chunker splits a document for the first time in
  this project's history, which is the regime F-004-6 says every M6 number has
  been measured outside of.
- It is **reversible by construction**: the digests carry their own
  `tenant_id`, so the 18-document baseline corpus can be restored with one
  `DELETE`. Cycle 003 refused this ingest partly because it destroys an
  attribution; tagging it means it does not have to.
- The interference is the **point**, not a side effect. Adding ~100× the chunks
  to the space the existing 16 E1 queries retrieve from is the RAG-side version
  of the scale question this project claims as its contribution. I expect
  context precision to **fall**. No criterion below requires any number to
  improve.

**A note on what C is not.** It does not make the corpus English, and the
reviews are Portuguese — that is a real limitation of what this corpus can
support and it gets written down, not engineered around.

## 3. DEVIATIONS

*(appended during the build, as they occur — §5.2)*

**DEVIATION 1 — C3/C5's "tenant_id distinct from `t_capstone_default`" is
unworkable as written, and reversibility moves to `doc_type` instead.**

While building C3, before any ingest ran: `orchestrator/main.py:108` sets
`tenant_id = cfg.tenancy.default_tenant` **unconditionally**, for every
query, with no code path that ever sends anything else — confirmed by
reading `mcp_client.py` (tenant_id bound at construction from that one
source) and `mcp/tools/vector_tools.py:214`
(`semantic_search`'s WHERE clause is always `dc.tenant_id = %(tenant_id)s`
against the session's tenant, unconditionally, **regardless of
`tenancy.enforced`**). This is A0.6, verbatim: *"It is never omitted, never
defaulted inside a function... In this build it always holds the value in
Appendix 1."*

Consequence: a document ingested under a genuinely distinct tenant_id (as
C3 specifies) would never be returned by `semantic_search` under the
current build, by design, not by oversight — which means C6's before/after
M6 comparison would show **zero difference**, not interference, because
the new corpus would be structurally invisible to retrieval. That defeats
the stated purpose of C6 (*"I expect context precision to fall... the
interference is the point"*) and would make the whole ingest measure
nothing.

The two ways to fix this were (a) modify the orchestrator/session tenant
threading so a query can target a second tenant, or (b) ingest under the
same tenant_id as baseline and use a different column as the isolation/
reversibility discriminator. (a) is a real code change to A0.6's threading
behavior and to the query path itself — out of scope (§2 "Explicitly NOT
this cycle" rules out new features, and multi-tenant query support is one),
and it is the kind of structural change that should be an explicit ask, not
a build-time judgment call. (b) costs nothing architecturally: `doc_type`
already distinguishes `review_digest` from the four baseline types by
migration 010's own CHECK constraint, no baseline document has ever used
it, and it is exactly as mechanical a `DELETE ... WHERE` target as
`tenant_id` would have been.

**Resolution: (b).** Both `documents.tenant_id` and `document_chunks.tenant_id`
for the ingested corpus are `t_capstone_default`, identical to baseline —
this is what makes the digests actually retrievable and lets C6 measure a
real number. Reversibility (C5) is demonstrated via
`DELETE ... WHERE doc_type = 'review_digest'` instead of a tenant_id
predicate. No line in A0.6, `session.py`, or the orchestrator's tenant
threading is touched. `scripts/gen_olist_review_digests.py`'s
`REVIEW_DIGEST_TENANT_ID` constant is kept as manifest-level provenance
metadata (recording which corpus a document came from) but is not what
isolates or reverses the ingest — `doc_type` is.

Not asked before acting: this is not a reversal of any §4.3 owner decision
(A0.6 itself is untouched; nothing about tenant_id semantics changes), and
proceeding under (b) is the more conservative of the two fixes, not the
riskier one — flagged here in full rather than silently, per §5.2, and
called out again in the outcome and confidence sections.

**DEVIATION 2 — the real ingest run exited 1 despite succeeding, on a
mistake of my own; not re-run, for a reason recorded here rather than just
asserted.**

`gen_olist_review_digests.py`'s manifest builder never actually set
`enforce_table_floor: false` in the manifest it writes, despite C3's ingest.py
change being built specifically to read that key. The real ingest (started
2026-08-21 00:07:34 UTC) ran to completion — all 2,567 documents, the
transaction committed (`Ingestion complete (transaction committed)` logged) —
and only THEN hit the post-commit Deliverable-2 floor check, which raised
`SystemExit(1)` because a review corpus has 0% `is_table` against a 15% floor
meant for the PDF corpus. Exit code 1, data correct.

Verified directly against the database, not inferred from the log: `documents`
2,585 (18 baseline + 2,567 review_digest), `document_chunks` 13,161 (36
baseline + 13,125 review_digest), 1,072 documents with >1 chunk, max 294
chunks for one document. C4 is satisfied by this count.

Fixed for future runs: `enforce_table_floor: false` added to the generator's
manifest output, confirmed by diff that `documents` is byte-identical between
the pre-fix and post-fix manifest — the fix touches only manifest metadata.

**Not re-run.** The completed ingest took just over two hours
(00:07:34–02:08:22 UTC) — 2,119 chunks needed the context-length fallback
split (DEVIATION-adjacent note, not itself a deviation: this is roughly 7x my
pre-ingest dry-run estimate of 313, because the dry run counted
whitespace-WORDS against the 512 target while the real failures are counted in
the embedding model's actual TOKENS, which are denser for Portuguese — see
`_embed_allowing_split`'s docstring). Re-running would cost another ~2 hours
to reproduce data already directly verified byte-for-byte correct in the
database, and the manifest diff already proves a fresh run would generate the
identical `documents` array. Spending two more hours to watch the same numbers
land again is not disciplined, it's theater — the verification that matters
(does the committed data match what the fixed script would produce) is done
and shown above.
