## 2. The plan

**Shape: correct the record, then remove the biggest confound under the
headline.**

Cycle 001 repaired the instrument and used it once. It produced a real headline
— `88.9% → 50.0%` — and published, alongside it, a defect-rate statistic that
is wrong by 4×, a failure analysis that is accurate for 3 of 8 cases, and a
credit to an automated check that never fired. None of those move the accuracy
numbers. All of them are in the report, and one of them (F-002-5) points the
next piece of engineering at the wrong subsystem. **Workstream A corrects the
record.** It is mostly text, plus two small guards and one test.

**Workstream B is the reason this cycle is worth a model switch.** F-002-10
found that `olist` shows the SQL agent **no join graph at all** — no foreign
keys, no primary keys — while the synthetic corpus shows it seventeen edges.
Every question in the hard fixture but one is join-bearing. BD6 records 2-hop
joins as this system's measured weakness across four independent checks. The
two failures F-002-5 reclassifies as schema grounding are precisely a missing
edge. That is a large, unmeasured confound sitting directly under the number
this project is about to put in a report.

**It is an experiment, not a fix, and that distinction is load-bearing.** This
repo has measured two schema-context interventions **harmful** (`a4293e1`,
schema comments) and one **helpful** (`da6e49f`, projection discipline). The
prior on reasoning here is bad and the prior on measuring is good. So B commits
to a paired before/after and **no threshold in either direction** — both
outcomes are publishable:

- **If FKs help:** the published real-data numbers were depressed by a
  corpus-preparation asymmetry the synthetic baseline never had, and *"needs a
  schema with a declared join graph"* becomes a stated deployment precondition
  — a genuine limitation, since plenty of enterprise warehouses declare none.
- **If FKs do not help:** a plausible confound under `50.0%` is retired and the
  7B's join failures are model capability, which strengthens the current claim
  rather than weakening it.

**Why the migration and not a code change.** Adding constraints changes the
prompt through a path that already ships and is already proven (it renders 17
edges on `public` today), so the experiment isolates one variable with **zero
orchestrator code**. If it helps, *then* building a join-hints source for
warehouses that cannot add constraints is justified by evidence. That is §5a's
own sequencing — watch it break, then implement against the observed failure —
applied one level down.

**Not in this cycle, and why.** Workstream A (multi-turn) is still the larger
build on the least-validated design in the repo. B1 (`x`/`x_local`) is still
gated on an M3 re-run that has not happened. C1 (auth) produces no number.
Top-*k* schema retrieval is **explicitly not started**: at nine tables
everything already fits the context, so selection is pure risk — and F-002-10
shows its stated safety property would be inert on the only real corpus anyway,
which is a reason to fix the corpus metadata first, not to build retrieval.

### The decision this plan needs from the owner

**Migration 008 departs from a recorded decision.** `migrations/007:31-36` says
*"NO CONSTRAINTS, DELIBERATELY … the DIRT IS THE POINT."* That is a `TRADEOFF`
under §4.2 with evidence predating the audit, and protocol says leave it and
cite it. I am asking rather than acting, with evidence 007 did not have: six of
the seven natural edges have **zero** orphans and would validate today without
touching a row. The dirt that motivated the decision lives on **one** edge
(`products → product_category_name_translation`, 13 orphans), and that edge is
handled explicitly rather than cleaned.

**Settled — owner, 2026-08-20.** Migration 008 goes in with the six clean edges;
the seventh is left **undeclared** rather than `NOT VALID`, so the dirty edge
stays dirty and stays visible. Scope confirmed as A + B as written. Both
recorded in the criteria below before the freeze, not after.

## 5. Confidence — where I would look if I were auditing me

Cycle 001's own §1 diagnosed cycle 000 precisely and then reproduced the
pattern in its own confidence section — five of six items were scope, and
the one "I might be wrong" item pointed at the one question that turned out
fine. I do not want to repeat that shape here, so several of these are
genuine doubts about my own reasoning, not just sample-size hedges.

**5.1 — My causal narrative in B5 claims more precision than I verified.** I
wrote that `ol_007`/`ol_018`'s regressions are "unrelated to any declared
edge," and for the six *foreign keys* that's true — neither query touches
`orders`↔`customers` or any of the `order_items` edges. But migration 008
also added **four PRIMARY KEYs**, including `products.product_id`, and
`ol_018` is exactly the query that started unnecessarily joining through
`products`. I did not test whether the PKs alone (with the FKs reverted)
would reproduce the regression — that would isolate which half of the
migration caused it, and I did not run that third arm. My "unrelated to any
declared edge" claim is accurate only if read as "unrelated to any declared
*foreign key*," and the document does not make that distinction explicit
enough. If I were auditing this cycle, I would run PKs-only and FKs-only as
two more paired arms before trusting the causal story over the correlational
one.

**5.2 — One paired run cannot separate a genuine effect from stochasticity
on the specific queries that flipped, and I have no repeated-trial baseline
to bound that.** The aggregate "before" numbers reproduced the published
values exactly, which rules out gross instrument drift — but it does not
tell me whether `qwen2.5:7b` at whatever temperature this stack runs at
would flip `ol_007`/`ol_018`/`oh_j09`/`oh_cs01` on a SECOND run of the
*identical* before-state, with no schema change at all. If four queries
flip on ordinary re-run noise as often as this experiment showed, the whole
finding is weaker than "declaring FKs net hurts" — it could be "this model
is noisy on ~4 of 34 queries regardless." I did not spend the second full
before-state run that would bound this, and the write-up's "does not
establish" line says so, but I want it said here too, plainly: I have not
ruled out that B's headline finding is mostly noise.

**5.3 — `m4_diagnosis_v2_corrected.json`'s provenance annotation (A4a) rests
on an inference I could not fully confirm.** The report was committed six
minutes after `diagnose_m4.py` gained the guard that would have stamped it,
yet carries no `flag_state` at all — not even a partial one. My best
explanation (the run predates the commit that bundled it with the code
change) is stated as inferred, not proven, in the file itself. If I'm wrong
about this, the four reconstructed values are still almost certainly correct
(they match the shipped config at every nearby commit I checked, and the
number itself — 36.0%/44.0% — has never moved across any of this project's
re-verifications), but the *reason given* for why the field is empty could
be wrong, and nothing forces a future reader to re-derive it independently.

**5.4 — A2b's partition-tie safeguard and A7a's table-count safeguard are
each tested against exactly the cases I already knew the answer to.** Both
self-tests demonstrate refusal by cloning a KNOWN-bad case (`oh_wf01` with
its tie-break statement stripped; `oh_wf03` with its old wrong label
restored) — which proves the mechanism works, but not that it will catch a
genuinely NEW defect of the same shape in a future fixture nobody has
audited yet. That is the same limit every guard in this repo has; I am
naming it rather than implying otherwise.

**5.5 — A3's `fixture_corpus()` is verified against all 12 current fixtures
(checked while writing this section, not during the build itself, and not
pinned by a test), but only 3 of them are exercised by
`test_fixture_corpus_guard.py`.** The other 9 resolve correctly right now —
I just confirmed it live — but nothing re-checks that on a future fixture
add or an `_about` block reformat for `phase_d_multilingual.json` or the
other 8. A parametrized test over every file in `fixtures/golden/` would
close this in about five lines and I did not write it, because A3's
criterion asked only for both directions to be demonstrated, which they
were.

**5.6 — D1's `oh_j04` drift (generator ahead of its committed fixture) was
found by accident, not by a systematic check, and I did not look for the
same class of drift anywhere else.** `phase_c2_v2.json`, `phase_d_
multilingual.json`, and the other five fixtures each have their own
generator script; I did not diff any of them against their committed JSON
to check whether the same "the script says one thing, the file says
another" gap exists elsewhere. Cheap to check, not done this cycle.

**5.7 — I did not re-measure the Gemini arm, and I want to be honest about
why beyond "no headroom."** The real reason is budget and time inside this
session, not a considered judgement that it adds nothing — a Gemini regression
on the EASY fixture (where it scored 94.4%, not 100%) is entirely possible
and B6's own criterion anticipated exactly this gap. "Single-provider" is
stated at every publication point, which is the honest minimum; it is not
the same as having checked.
