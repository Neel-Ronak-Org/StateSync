Can a typed decision model make an assistant's decisions?

An assistant that answers from a SQL database and company filings makes small decisions on every question. We tested whether Jev, a model that returns probabilities instead of text, can make four of them.

The pattern across all four: Jev does well when the answer can be read off the text in front of it, and poorly when it has to be worked out or when one decision is split into separate questions.

The documents engine, step by step

1Find documentsDense search (mxbai-embed-large) over 44,918 passages of 84 filings picks the most relevant filings.
2Search within themA second search inside those filings returns up to 25 passages.
3Re-rank (optional)A cross-encoder (bge-reranker-v2-m3, on GPU) re-scores them, reading each filing's title.
4OrderDense score, cross-encoder score, or Jev's P(passage contains the answer).

Across all 300 test questions

Same 25 passages, different order. Jev over the cross-encoder's list puts the source page first 53.3% of the time against 43.7% for the cross-encoder's own ranking (p < 0.0001). Page@8 barely moves: it depends on what the search found, not on order.

What this costs

The "product display order" regroups the top 8 by filing and page position. An earlier test compared Jev against that order by mistake; the fair baseline is the cross-encoder's own ranking.

Routing accuracy, 180 new questions (R2)

Jev asked one four-way choice is not significantly different from the LLM router (p = 0.25) and needs no LLM call: 1.9 s against 9.3 s. Asked two separate yes/no questions, it drops 12.8 points.

Telling the router what the database covers (R4)

Without coverage, every model router sent questions about absent companies to SQL. Listing the companies, metrics and date ranges in the database card fixed most of them.

Example questions

Spotting a wrong SQL answer (393 BIRD questions)

AUROC for flagging the pipeline's first answer as wrong. Jev, with no training, is not significantly different from the LLM judge or the fine-tuned ModernBERT.

Choosing and falling back

Jev doubts well but chooses poorly: picking its highest-scoring candidate barely beats the first answer. Used only as the trigger, it falls back on 13.5% of questions.

Can this database answer the question? (298 questions, hard negatives)

Each question was shown its own schema, the schema without the tables its query reads, and the schema without the columns it reads. Word overlap is a simple baseline. At a 1% false-refusal limit Jev still catches only about half of the unanswerable cases.

Rules we held ourselves to

Hypotheses, measures, tests and baselines were committed to the repository before each question set existed. Every later change is in a change log.

No test question was seen while the systems were designed. FinanceBench served only for development.

Two systems are called comparable only when the 95% interval of their difference lies within ±8 points; better or worse only on a significant test.

Every number in the paper is generated from the result files, never typed by hand.

What the audits changed

An early page-finding test compared Jev with the pipeline's display order. Against the cross-encoder's real ranking the gap shrank, so we built a fresh set and tested again.

An early routing test reused development questions; it was replaced by 180 new ones.

The first answerability test used easy negatives (the wrong database); it was replaced by schemas with the needed tables or columns removed.

Independent audits of the draft corrected wording that went beyond the evidence.
