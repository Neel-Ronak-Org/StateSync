### F-007-1 The strategy section that defines this cycle's direction states a fact about the code that is false

**Rank: this-cycle.** `V2_STRATEGY.md` §3/§3b is the owner-set direction for
cycle 007. §3b sizes the work with a specific claim about what already exists.
The claim is wrong, and the error is in the optimistic direction.

The claim, verbatim (`docs/V2_STRATEGY.md:149`):

> `/query` already accepts `session_id` and threads it to `MCPSession`, so half
> the plumbing exists.

Three checks. First, does `MCPSession` accept a session id at all?

```
$ sed -n '32,40p' orchestrator/mcp_client.py
    def __init__(self, tenant_id: str, base_url: str | None = None) -> None:
        self.tenant_id = tenant_id
        self.session_id = str(uuid.uuid4())
```

It does not. It takes `tenant_id` and `base_url`, and **mints its own
unrelated uuid4**. Second, what do the call sites pass?

```
$ grep -rn "MCPSession(" --include="*.py" orchestrator scripts tests | grep -v "class MCPSession"
orchestrator/nodes/unstructured_knowledge.py:328:    async with MCPSession(tenant_id=tenant_id, base_url=mcp_base_url) as session:
orchestrator/nodes/sql_agent.py:381:    async with MCPSession(tenant_id=tenant_id, base_url=mcp_base_url) as session:
```

Neither passes it, because there is no parameter to pass it to. Third, does the
request-level `session_id` reach anything downstream?

```
$ grep -rn "session_id" --include="*.py" --include="*.js" --include="*.html" \
      orchestrator mcp frontend migrations scripts tests | grep -v __pycache__
orchestrator/main.py:76:    session_id: str | None = None
orchestrator/main.py:107:    session_id = request.session_id or str(uuid.uuid4())
orchestrator/main.py:114:        "session_id": session_id,
orchestrator/main.py:125:                session_id=initial_input["session_id"],
orchestrator/mcp_client.py:34:        self.session_id = str(uuid.uuid4())
orchestrator/mcp_client.py:48:                "X-Session-ID": self.session_id,
orchestrator/state.py:111:    "session_id",
orchestrator/state.py:123:    session_id:   str
orchestrator/nodes/entry.py:38:    session_id: str = state_dict.get("session_id") or str(uuid.uuid4())
orchestrator/nodes/entry.py:48:        "session_id": session_id,
mcp/main.py:176:    session_id = request.headers.get("X-Session-ID", "")
mcp/session.py:39:        session_id=session_id or str(uuid.uuid4()),
```

The request's `session_id` is written into `StateSyncState`, marked immutable,
put in no trace, read by no node, and **never leaves the orchestrator process**.
The `X-Session-ID` that MCP actually receives is a different value, minted per
`MCPSession` object — so a single hybrid query already emits *two* unrelated
session ids, one per node that opens a session.

And the frontend never supplies one:

```
$ grep -rn "session" frontend/ | grep -v node_modules
(no output)
```

**What the plumbing actually is.** One nullable request field that is stored and
never read. Not "half"; a named field and nothing behind it. The three things
§3b's design needs — a history table, a carryover read, and an identity to scope
it by — are all absent, which §3 already says ("0% built"). What is new here is
that the **one** component §3b counted as already done is not done either.

**Does not establish:** that multi-turn is harder than §3b estimates overall —
adding a `session_id` parameter to `MCPSession` is a small change, and the
rewrite-before-supervisor design §3b proposes is untouched by this. It
establishes only that the specific "half the plumbing exists" premise is false
and that the session-id threading is work, not inheritance. It also does not
establish anything about whether `X-Session-ID` *should* be the request's
session id — MCP treats it as a per-connection identifier and nothing today
depends on the two agreeing.

**Bucket: DEFECT.** §4.2 requires a TRADEOFF's justification to predate the
audit. There is no record anywhere of a decision that `MCPSession` should mint
its own id; `mcp_client.py`'s own module docstring describes the session as
"bound at session establishment", which is consistent with either reading. The
strategy sentence is simply a claim nobody checked.

### F-007-2 The hybrid route's SQL sub-task ignores `target_schema` and always queries the synthetic corpus

**Rank: this-cycle.** This is a live silent-wrong-answer path on the exact route
`V2_STRATEGY.md` §3a's cross-modal multi-turn work runs over.

`schema_retriever.py` carries a comment describing an incident and its fix:

```
$ sed -n '85,90p' orchestrator/schema_retriever.py
            # QUALIFY the name when the corpus is not the default schema.
            # Without this the agent is handed "TABLE orders:" and writes
            # `FROM orders`, which resolves through search_path to PUBLIC --
            # so it queries the 550-row synthetic corpus while being scored
            # against 99,441 real rows. Observed exactly that on the first
            # Olist run before the qualification was added.
```

The fix was applied to one of the two call sites.

```
$ grep -rn "\.retrieve(" --include="*.py" orchestrator | grep -v .venv
orchestrator/nodes/unstructured_knowledge.py:277:    schema_context, _ = await retriever.retrieve(session, table_names)
orchestrator/nodes/sql_agent.py:415:                schema_context, table_descriptions = await retriever.retrieve(session, table_names, _schema)
orchestrator/nodes/sql_agent.py:477:            schema_context, _ = await retriever.retrieve(session, table_names, _schema)

$ grep -n "_schema" orchestrator/nodes/sql_agent.py | head -3
383:        _schema = target_schema()
384:        tables_result = await schema_list_tables(session, _schema)
415:                schema_context, table_descriptions = await retriever.retrieve(session, table_names, _schema)
```

`sql_agent.py` resolves `target_schema()` and passes it to **both**
`schema_list_tables` and `retrieve`. `unstructured_knowledge.py::_run_sql_subtask`
— the hybrid route's SQL half — passes it to **neither** (`schema_list_tables(session)`
at line 272, `retrieve(session, table_names)` at line 277). Both default to
`schema=None`, which MCP resolves server-side to `public`.

What the two paths are handed, live, at the MCP layer:

```
$ curl -s -H 'X-Tenant-ID: t_capstone_default' -X POST http://localhost:8080/rpc \
    -d '{"jsonrpc":"2.0","id":"a","method":"schema.list_tables","params":{}}'
n= 12 ['catalog_items', 'delivery_events', 'disputes', 'document_chunks',
       'documents', 'fulfillments', 'locations', 'logistics_providers',
       'network_participants', 'order_items', 'orders', 'sellers']

$ curl -s -H 'X-Tenant-ID: t_capstone_default' -X POST http://localhost:8080/rpc \
    -d '{"jsonrpc":"2.0","id":"b","method":"schema.list_tables","params":{"schema":"olist"}}'
n= 9 ['customers', 'geolocation', 'order_items', 'order_payments',
      'order_reviews', 'orders', 'product_category_name_translation',
      'products', 'sellers']
```

**Why it is silent rather than an error.** The two schemas share three table
names — `orders`, `order_items`, `sellers`. Under `target_schema = "olist"` the
hybrid sub-task is shown `public`'s 550-row `orders`, writes `FROM orders`,
resolves through `search_path` to `public.orders`, and returns a well-formed
count of the wrong corpus. No exception, no empty result, no classifier hit.
That is the `80d35c8` failure mode `shipped_flags.py` was built to prevent,
surviving on a route the guard's fixture/corpus check never covers because no
fixture exercises hybrid-over-olist.

The shipped default is `target_schema = "public"` (`config/flags.toml:174`), so
the two paths agree today and **no published number is affected**. It fires the
moment anyone follows `AGENT_HANDOFF.md` §6's own instruction — *"Point the
agent at it with `schema_retriever.target_schema = "olist"`"* — and asks a
hybrid question.

**Does not establish:** that any measurement in this repo was taken through this
path — none was; every real-data number comes from the `sql` route, and M6 runs
on `public`. It does not establish that the hybrid route is otherwise correct
(its SQL sub-task is single-shot with no correction loop by design), and it does
not establish what the right fix is: passing `target_schema` through is one
option, refusing to run hybrid under a non-default schema is another, and this
audit did not measure either.

**Bucket: DEFECT.** No document records a decision to exempt hybrid from
`target_schema`; the qualification comment reads as a general fix and was
applied partially.

### F-007-3 M3's scorer names a definition it does not implement; the gap is worth 12.5pp on the shipped build and inverts one comparison's direction

**Rank: this-cycle.** D-V1 is a published number, it is one half of Workstream
B1's pre-committed acceptance condition, and it is cited in `AGENT_HANDOFF.md`
§5 as evidence in an **OWNER decision** (§4.3: the migrations 005/006 revert).

`bench_multilingual.py` and `check_consistency.py` sit in the same directory,
each define a function called `_signature`, and each claims the same authority:

```
$ grep -n -A2 "def _signature" scripts/bench_multilingual.py scripts/check_consistency.py
scripts/bench_multilingual.py-79-    """Execution-based dataframe equality, value-only (C1-V3/C2-V8 definition):
scripts/check_consistency.py-47-    """Canonical, order-independent signature for dataframe equality."""
```

`check_consistency.py`'s module docstring quotes the spec text it implements:
*"column-set equality plus row-multiset equality, column order and row order
ignored (same definition as C1-V1's reference, C1-V3 spec text)"*. It includes
the column names in the signature. `bench_multilingual.py` replaces column-set
equality with a bare **count** (`"n_columns": len(sql_columns)`) and sorts each
row's values among themselves, discarding which column each value came from.

Both functions, copied verbatim out of their files and run on the same inputs:

```
case                                              M3 says equal   M5 says equal
A. same values, DIFFERENT column names            True            False
B. two aggregates SWAPPED between their columns   True            False
C. genuinely different data (control)             False           False
```

Case C is the control: both agree when the data really differs. Case A is the
alias-insensitivity M3's docstring gives a reason for. Case B is the one nobody
wrote down: a query returning `{delayed: 9, on_time: 5}` against a ground truth
of `{delayed: 5, on_time: 9}` scores **correct** under M3, because the two
values are sorted within the row before comparison.

**How much it is worth on the number that ships.** Re-executing every
`match=True` treatment query's own `executed_sql` and its fixture's
`ground_truth_sql` live, and re-scoring under both definitions:

```
SHIPPED build (post-projfix)
  published D-V1 treatment            : 22/40 = 55.0%
  passes lost under the NAMED (C1-V3) definition: 5
      d_ml_003: gt_cols=['sum']   vs generated_cols=['total_order_value']
      d_ml_004: gt_cols=['sum']   vs generated_cols=['total_order_value']
      d_ml_023: gt_cols=['sum']   vs generated_cols=['total_order_value']
      d_ml_024: gt_cols=['sum']   vs generated_cols=['total_order_value']
      d_ml_039: gt_cols=['count'] vs generated_cols=['b2b_order_count']
  D-V1 treatment under that definition: 17/40 = 42.5%

migration 005 (REJECTED)
  published D-V1 treatment            : 22/40 = 55.0%
  passes lost under the NAMED (C1-V3) definition: 3
      d_ml_004, d_ml_011, d_ml_013   (all `sum`/`count` vs a descriptive alias)
  D-V1 treatment under that definition: 19/40 = 47.5%
```

**Read this the right way round.** Every one of those eight flips is a pure
column-alias difference. **M3's loose definition is the correct one** and the
strict C1-V3 definition would manufacture eight false failures. This finding is
*not* "D-V1 is overstated." It is:

1. **The docstring names a definition the code deliberately does not implement**,
   and the file that does implement that definition is three directories along.
   A reader checking D-V1 against "the C1-V3 definition" is checking it against
   the wrong thing.
2. **The choice is worth 12.5pp** on the shipped build (55.0% → 42.5%) and is
   recorded nowhere as a choice.
3. **It is load-bearing on the direction of a comparison.** Under the definition
   M3's own docstring names, the rejected migration 005 **outscores** the shipped
   build on D-V1 (47.5% vs 42.5%) — the reverse of the published ordering.

**Does not establish:** that the migrations 005/006 revert is wrong. It is not
reopened here and this audit does not propose reopening it. `open_items.md`
already identifies D-V2 (81.25% vs 62.5%) as *"the clause that actually rejected
migration 005"*, and D-V2 is untouched by this finding — it scores entity strings
in SQL text, not result sets. D-V1 was never the deciding clause. This also does
not establish that case B (swapped aggregates) has ever produced a wrong pass:
**it has not** — all eight observed flips are alias-only, and I found no
instance of case B in the 40-query fixture. Case B is a demonstrated property of
the scorer, not a demonstrated error in a published number.

**Bucket: split, deliberately.**
- **TRADEOFF** for the alias-insensitivity itself. Justification predates this
  audit and is cited per §4.2: the docstring at `scripts/bench_multilingual.py:79-81`
  — *"ground_truth_sql and the generated SQL are independently authored, so
  column aliases legitimately differ even when the data is identical."* The
  re-scoring above confirms that reasoning empirically. Leave the behaviour.
- **DEFECT** for the label and for case B. Citing "(C1-V3/C2-V8 definition)" for
  a definition that is measurably not C1-V3's is a claim nothing checked, and
  the within-row value sort has no recorded rationale anywhere and is not
  required by alias-insensitivity.

### F-007-4 The A2 concurrency assertion — spec'd "active in all environments including production" — cannot fire in the graph

**Rank: open_items.** No number depends on it. It is here because it is a
locked-spec deliverable that the repo asserts it implements, and because
Workstream A adds state to exactly the machinery it guards.

The spec is unambiguous (`docs/StateSync_Build_Spec.md:193`):

> A last-write-wins field written by two concurrent nodes is a defect — the
> merge is nondeterministic and will surface as an M2 failure. **Enforce with an
> assertion in the merge path, active in all environments including production.**

and `:686` requires *"`orchestrator/state.py` implementing A2 in full, including
the concurrency assertion."* The assertion exists and works in isolation. It
cannot fire in the graph, because `graph.py` destroys its state on every hop.

Run inside the **running container**, not the repo:

```
$ docker compose exec -T orchestrator python /dev/stdin < probe_lww.py
after supervisor, _lww_writers = {'route': 'supervisor'}
assertion fired: Concurrency violation: field 'route' was written by node
  'supervisor' and again by node 'sql' in the same concurrent dispatch. [...]

--- simulating graph.py's wrapper round-trip ---
'_lww_writers' present in model_dump()? -> False
rebuilt._lww_writers = {}
different node wrote 'route' after round-trip: NO ASSERTION. route = docs
```

The mechanism: `merge()` records the writing node in `_lww_writers`, a private
attribute set via `object.__setattr__` and excluded from serialization.
`graph.py`'s wrapper immediately calls `.model_dump()` on the result
(`orchestrator/graph.py:164`), LangGraph rebuilds a `StateSyncState` from that
dict for the next node, and `model_post_init` resets `_lww_writers` to `{}`
(`orchestrator/state.py:175-176`). Every node therefore begins with an empty writer
map, `prior_writer` is always `None`, and the assertion is unreachable.

The corroborating tell is that the function written to manage this is dead:

```
$ grep -rn "reset_lww_writers" --include="*.py" orchestrator tests scripts mcp
orchestrator/graph.py:58:from state import StateSyncState, merge, reset_lww_writers
orchestrator/state.py:282:def reset_lww_writers(state: StateSyncState) -> StateSyncState:
```

Imported by `graph.py`, defined in `state.py`, **called nowhere**. There is even
a comment marking where it was meant to go — `orchestrator/graph.py:188`,
*"# Reset LWW writer tracking at start of sequential dispatch (not parallel here)"*
— above a line that does not do it. Its docstring says it exists because without
it "a sequential node that writes the same field twice would incorrectly trigger
the assertion", which is only a concern if tracking persists across nodes. It
does not. The design is internally inconsistent in both directions: as built the
assertion is vacuous, and if the tracking were made to persist without the reset
being called, it would fire on legitimate sequential writes instead.

No test covers `state.py` at all (`ls tests/` — eleven files, none of them).

**Does not establish:** that any defect has been missed because of this. The
shipped graph has **no parallel dispatch** — `supervisor` routes to exactly one
of `sql`/`docs`/`hybrid` — so there is currently nothing for the assertion to
catch, and I found no evidence of an actual nondeterministic merge. It
establishes that a locked-spec guarantee is unimplemented as specified and that
the safety net will still be absent if a future cycle adds a parallel node. It
also does not establish that `merge()` itself is wrong: the SUM/APPEND/immutable
dispatch all work, and only the concurrency arm is dead.

**Bucket: DEFECT.** Nothing predating this audit records a decision to defer the
assertion; the spec, the docstring and the dead import all assert the opposite.

### F-007-5 The SchemaRetriever seam's Protocol and its only implementation disagree, and the gate that passes it is a grep for the class declaration

**Rank: open_items.** No number moves. It is the mechanism behind F-007-2 and it
matters for §5a's pre-committed top-k retriever, which is written to this seam.

```
$ grep -n -A4 "class SchemaRetriever(Protocol)" orchestrator/schema_retriever.py
class SchemaRetriever(Protocol):
    async def retrieve(
        self, session: MCPSession, table_names: list[str],
    ) -> tuple[str, list[dict]]:

$ grep -n -A3 "class DirectSchemaRetriever" orchestrator/schema_retriever.py
class DirectSchemaRetriever:
    async def retrieve(
        self, session: MCPSession, table_names: list[str],
        schema: str | None = None,
    ) -> tuple[str, list[dict]]:
```

The Protocol does not declare the `schema` parameter that the shipped
implementation requires in order to reach the real-data corpus at all, and that
`sql_agent.py` passes positionally at two call sites. A second implementation
written to the declared interface — which is precisely what §5a's top-k
candidate selector would be — would satisfy `SchemaRetriever` and break
`sql_agent.py` on the third positional argument.

`@runtime_checkable` does not help: `isinstance()` against a runtime-checkable
Protocol checks method *names*, not signatures. Nothing calls it anyway:

```
$ grep -rn "isinstance.*SchemaRetriever\|isinstance.*TrajectoryStore" --include="*.py" orchestrator scripts tests
(no output)
```

And what the seams gate — reported as 26/26 — actually asserts about this seam:

```
$ sed -n '85,89p' scripts/verify_seams.py
    # 3. CSR-RAG hypergraph retrieval -> SchemaRetriever, C1
    p = REPO_ROOT / "orchestrator" / "schema_retriever.py"
    check("SchemaRetriever Protocol exists", grep(r"class SchemaRetriever\(Protocol\)", p))
    check("schema_retriever.provider resolved at a real dispatch point",
          grep(r"flags\.schema_retriever\.provider", p) and grep(r"def get_schema_retriever", p))
```

A regex for the class declaration line. The check named "SchemaRetriever
Protocol exists" is true of any file containing that string, and stays true
however far the Protocol drifts from the thing that implements it.

**Does not establish:** that the other seams are checked this way — I read this
one and did not audit the remaining 24 assertions, so "the seams gate is
grep-shaped" is **not** a claim this audit makes. It does not establish that
anything is broken today: there is one implementation, `DirectSchemaRetriever`,
and it works because its callers pass what it needs rather than what the
Protocol declares.

**Bucket: DEFECT.** `schema_retriever.py`'s own docstring states the seam's
purpose is that *"a future HypergraphSchemaRetriever would plug in here without
changing SQL Agent call sites"* — the drift defeats the stated purpose, so it is
not a recorded tradeoff.

### F-007-6 `run_e2_v1.py` (M7) crashes on an unregistered argparse attribute, in the guard that exists because two harnesses destroyed committed baselines

**Rank: open_items.** Fails safe (crashes rather than overwrites), so nothing was
lost. It is reported because it is exactly what "never run" buys you.

```
$ python3 scripts/run_e2_v1.py --out docs/metrics-report.md
Traceback (most recent call last):
  File "/Users/neeljaiswal/StateSync/scripts/run_e2_v1.py", line 152, in <module>
    sys.exit(main())
  File "/Users/neeljaiswal/StateSync/scripts/run_e2_v1.py", line 82, in main
    if args.out.exists() and not args.force:
                                 ^^^^^^^^^^
AttributeError: 'Namespace' object has no attribute 'force'

$ grep -n "force" scripts/run_e2_v1.py
82:    if args.out.exists() and not args.force:
84:              f"--out, or pass --force to deliberately replace it.")

`--force` is read, and advertised in the error text the script would print, but
never registered on the parser. The only harness that does register it is
`experiment_tool_ceiling.py`. The branch is short-circuited whenever `--out`
points at a new path, which is why every successful run has missed it: the bug
is reachable **only** on the append-only guard's own trigger.

**Does not establish:** anything about M7 as a number, or about the other 29
queries' behaviour — the crash is before any query runs, and this audit did not

### F-007-7 The supervisor's route-parse fallback iterates a `frozenset`, so it is nondeterministic across processes

**Rank: open_items.** M9 routing determinism is published at 0.983 and this path
is the fallback, not the main one.

```
$ sed -n '96,99p' orchestrator/nodes/supervisor.py
    # Regex fallback
    for candidate in _VALID_ROUTES:
        if re.search(rf'\b{candidate}\b', text, re.IGNORECASE):
            return candidate
```

`_VALID_ROUTES` is `frozenset({"sql", "docs", "hybrid"})`. Python randomizes
string hashing per process unless `PYTHONHASHSEED` is set, so iteration order —
and therefore which route wins when the LLM's text mentions more than one —
changes between orchestrator restarts. In the running container:

```
$ docker compose exec -T orchestrator sh -c 'echo "PYTHONHASHSEED=${PYTHONHASHSEED:-<unset>}"; \
    for i in 1 2 3; do python -c "print(list(frozenset({\"sql\",\"docs\",\"hybrid\"})))"; done'
PYTHONHASHSEED=<unset>
['docs', 'hybrid', 'sql']
['hybrid', 'sql', 'docs']
['sql', 'docs', 'hybrid']
```

Three orders in three processes. A response like *"this is not sql, it is docs"*
resolves to whichever of the two the set happens to yield first in that
container's lifetime.

**Does not establish:** that this has ever changed a routing decision. The
fallback runs only when the JSON parse fails, I did not measure how often that
happens, and M9's 0.983 was measured on a single process where the order was
fixed for the whole run — so the published figure is internally consistent
regardless. It establishes a reproducible source of cross-restart
nondeterminism in a component whose headline property is determinism.

**Bucket: DEFECT.** No document records set-iteration order as a considered
choice.

### F-007-10 M3 does not reproduce — the headline moved 7.5pp on an unchanged build, and the seed the config declares is sent to no model

**Rank: this-cycle.** D-V1 and D-V2 are published numbers, quoted to one decimal
place, and one of them is half of Workstream B1's pre-committed acceptance
condition. This is the **first time M3 has been re-run since 2026-08-17**, and
it is the first evidence anywhere of what M3's run-to-run variance actually is.

The run: `bench_multilingual.py`, shipped flags (guard confirms
`"shipped": true`), same fixture, same local `qwen2.5:7b`, same corpus, no code
change between the two measurements on any path D-V1 exercises.

```
                                  committed 2026-08-17  this audit 2026-08-24
D-V1 control                      16/40 = 40.0%          15/40 = 37.5%   (-2.5pp)
D-V1 treatment                    22/40 = 55.0%          25/40 = 62.5%   (+7.5pp)
English reference                 11/20 = 55.0%          10/20 = 50.0%   (-5.0pp)
D-V2 entity preservation          26/32 = 81.2%          27/32 = 84.4%   (+3.1pp)

treatment queries GAINED (3): ['d_ml_008', 'd_ml_030', 'd_ml_037']
treatment queries LOST   (1): ['d_ml_018_en']
```

**Why this is not simply "the 7B is stochastic, everybody knows."** The project
believes it has pinned sampling. `config/statesync.toml` declares both controls:

```
$ grep -n -A2 "\[models\]" config/statesync.toml
157:[models]
158:temperature               = 0.0
159:seed                      = 20260807
```

Temperature is honoured. **The seed is read by nothing.**

```
$ grep -rn "models.seed\|cfg.models.seed\|\"seed\"" --include="*.py" orchestrator mcp scripts tests evaluator | grep -v .venv
scripts/gen_seed_fixture.py:25:# Seed for reproducibility — matches config.models.seed from Appendix 1
scripts/check_review_probe_rank.py:167:        "probe_set_seed": probe_set["seed"],
scripts/gen_review_probe_set.py:96:        "seed": SEED,

$ sed -n '55,63p' orchestrator/llm/adapters/ollama_adapter.py
            "options": {
                "temperature": cfg.models.temperature,
                "num_predict": max_tokens,
            },
```

`cfg.models.seed` is referenced **nowhere in the orchestrator**. The three hits
are fixture-generation scripts with their own local constants — and
`gen_seed_fixture.py:25`'s comment claims a correspondence ("matches
config.models.seed") that is not wired to anything. Ollama's `options` object
accepts a `seed` key; the adapter never sends it. Neither do the Anthropic,
Azure or Gemini adapters (`grep -rn "seed" orchestrator/llm/` → no output).

So the repo declares a reproducibility control, states in a comment that a
fixture matches it, and passes it to no model on any provider.

**The consequence that actually bites.** `open_items.md`'s amended B1 condition
(audit 001 F-001-3) requires *"D-V1 treatment must not fall below the paired
pre-measurement taken on the same build immediately before the attempt."*
Pairing was the right instinct and the amendment is not challenged here — but
it was written without knowing the noise floor, and a **±7.5pp** floor means a
paired D-V1 comparison cannot detect a real effect smaller than that. The
D-V2 clause is in better shape (moved 3.1pp) but is stated as an absolute to
two decimals (`≥ 81.25%`) against a measurement that just moved 3.1pp.

**Does not establish:** *why* it moved. Two runs is not a variance estimate —
it is one difference, and I did not run M3 a third time to separate sampling
noise from a real change in the build between 08-17 and today. It does not
establish that the seed is the cause: at `temperature = 0.0` Ollama is already
near-deterministic, so an unsent seed may be a latent defect rather than this
run's explanation, and I did not test whether sending it removes the variance.
It does not establish that D-V2's 81.25% bar is unsafe — 84.4% clears it — only
that the margin is of the same order as the movement. It does **not** establish
anything about the migrations 005/006 revert, which rests on a 18.7pp D-V2 gap,
far outside this movement.

**Run-condition disclosure, because it is a measurement (§6 class 9).** The run
took 5h24m wall-clock, against my own ~60–90 min estimate, which was wrong.
Per-query latency was **normal**: mean inter-query gap excluding stalls was
**61.0s over 38 intervals**, inside the ~20–70s the handoff documents. The
excess is six stalls of 18–36 minutes (2152s, 2012s, 1975s, 1906s, 1090s,
1089s) totalling ~2.8h, spanning a session gap in which the host slept. The
stalls fall **between** queries, not inside them; no flag changed and no
restart occurred except the two pass boundaries the script itself performs.
`ps` was clean before and after. I cannot retroactively prove nothing else ran
during those windows, and I am recording that rather than asserting a clean
run.

**Bucket: DEFECT** — for the unwired seed and the false comment in
`gen_seed_fixture.py:25`. The *variance itself* is not a defect and is not
bucketed as one; it is a previously unmeasured property, which is why it is
reported as a measurement rather than a fault.

## Flag-state restoration

`bench_multilingual.py` mutates `config/flags.toml` by design (it varies
`normalization.enabled` as its control/treatment variable) and restores the
shipped value only as a side effect of the treatment pass running last. A
snapshot was taken before the run and diffed after:

IDENTICAL — flag state restored

  "live_staleness": null,
  "fixture_corpus_check": null
```

Working tree clean at the audit commit apart from the audit file itself.

**Worth recording for whoever runs M3 next:** the restoration is incidental,
not designed. If the run dies during the *control* pass — which is where 5 of

a non-shipped state that the guard will then correctly refuse to run under.
That is a fail-safe, but it is not obvious from the script, and a killed M3 is
exactly the situation in which someone re-runs without checking.

## Time actually spent

The owner set ~90 minutes. **The audit took roughly 90 minutes of working time
and 5h24m of wall-clock**, and the difference is one decision: the owner was
asked whether to run M3 fully, given an explicit estimate that it would consume
the whole box, and chose "run it fully, blow the box." That was the right call

## The one thing I would tell the next auditor

Six cycles have audited artifacts — fixtures, reports, corpora, gates. This one
audited **code**, because the owner pointed at it, and the hit rate was higher
per minute than anything else in this audit. Five of the ten findings are in
`orchestrator/`, a directory six cycles had touched once. The reason is not
that the code is bad; it is that the project's verification effort is aimed
almost entirely at *numbers*, and a claim in a docstring, a Protocol signature,
or a dead import is not a number. `tests/` has eleven files and not one of them
imports `orchestrator/state.py`.
