### F-005-1 The frontend has sent no security headers since `56a23bf`, and every check that could have caught it reads the config file instead of a response

**Rank: `PUBLISHABLE`. Bucket: `DEFECT`.**

`README.md:234` ticks Deliverable 8: *"Stateless frontend UI with strict CSP
headers (no `unsafe-eval`)"*. `StateSync_Build_Spec.md:979` makes "CSP headers
set and verified" an acceptance item. `verify_e2.py`'s E2-V4 block asserts five
separate properties of that CSP and passes all five. The running server sends
no CSP at all — nor X-Frame-Options, X-Content-Type-Options, or
Referrer-Policy.

**What I ran.**

```
$ curl -s -D - -o /dev/null http://localhost:3000/ | tr -d '\r'
HTTP/1.1 200 OK
Server: nginx/1.27.5
Date: Thu, 20 Aug 2026 18:37:52 GMT
Content-Type: text/html
Content-Length: 14410
Last-Modified: Thu, 20 Aug 2026 18:07:57 GMT
Connection: keep-alive
ETag: "6a87427d-384a"
Cache-Control: no-cache
Accept-Ranges: bytes
```

No `Content-Security-Policy`. Not one path is different:

```
$ for p in / /index.html /app.js /nonexistent /favicon.ico "/?x=1"; do ... done
/                -> HTTP 200 | sec-headers: 0
/index.html      -> HTTP 200 | sec-headers: 0
/app.js          -> HTTP 200 | sec-headers: 0
/nonexistent     -> HTTP 200 | sec-headers: 0
/favicon.ico     -> HTTP 200 | sec-headers: 0
/?x=1            -> HTTP 200 | sec-headers: 0
```

(`sec-headers` counts CSP + X-Frame-Options + X-Content-Type-Options +
Referrer-Policy in the response.)

**The mechanism.** nginx's `add_header` is inherited into a `location` block
**only if that block declares no `add_header` of its own**. `56a23bf` added two
location blocks, each with a `Cache-Control` header, which discarded all four
inherited security headers for exactly the two files that matter:

```
$ docker exec statesync-frontend-1 nginx -T | grep -nE "add_header|location|server \{"
137:server {
146:    add_header Content-Security-Policy "default-src 'self'; script-src 'self' ...
156:    add_header X-Frame-Options DENY always;
157:    add_header X-Content-Type-Options nosniff always;
158:    add_header Referrer-Policy no-referrer always;
176:    location = /index.html {
177:        add_header Cache-Control "no-cache" always;
180:    location = /app.js {
181:        add_header Cache-Control "no-cache" always;
186:    location / {
193:    location /nginx-health {
195:        add_header Content-Type text/plain;
```

`location /` declares none, but its `try_files $uri $uri/ /index.html` performs
an internal redirect into `location = /index.html`, so every HTML response
loses them too. `always` does not help: it controls response-code filtering,
not inheritance.

**Attribution — measured, not inferred.** I ran the pre-commit and post-commit
configs side by side in throwaway containers rather than reasoning from the
documentation:

```
$ git show 56a23bf^:frontend/nginx.conf > old_nginx.conf
$ git show 56a23bf:frontend/nginx.conf  > new_nginx.conf
$ docker run -d --name csptest-old -p 3090:80 -v .../old_nginx.conf:... nginx:1.27-alpine
$ docker run -d --name csptest-new -p 3091:80 -v .../new_nginx.conf:... nginx:1.27-alpine

--- old config (56a23bf^), port 3090 ---
  /index.html  HTTP:200 CSP:1 XFO:1 XCTO:1 RP:1 CacheControl:0
  /app.js      HTTP:200 CSP:1 XFO:1 XCTO:1 RP:1 CacheControl:0
--- new config (56a23bf), port 3091 ---
  /index.html  HTTP:200 CSP:0 XFO:0 XCTO:0 RP:0 CacheControl:1
  /app.js      HTTP:200 CSP:0 XFO:0 XCTO:0 RP:0 CacheControl:1
```

Four security headers traded for one cache header, silently, in a commit whose
message is about caching. `git log -S 'location = /index.html' -- frontend/nginx.conf`
returns `56a23bf` and nothing else.

**Why five passing checks did not see it.** E2-V4 reads the file:

```
$ sed -n '129,141p' scripts/verify_e2.py
def e2_v4_csp() -> None:
    section("E2-V4 — CSP forbids unsafe-eval (header inspection)")
    conf = NGINX_CONF.read_text()
    csp_lines = [ln for ln in conf.splitlines() if "Content-Security-Policy" in ln]
    check("exactly one CSP header directive", len(csp_lines) == 1, ...)
    ...
    check("CSP contains no 'unsafe-eval'", "unsafe-eval" not in csp)
    check("CSP sets object-src 'none'", "object-src 'none'" in csp)
    check("CSP sets frame-ancestors 'none'", "frame-ancestors 'none'" in csp)
```

The section is literally named *"header inspection"* and inspects no header.
And it is the only such reference in the codebase:

```
$ grep -rniE "curl.*-I|-D -|response\.headers|Content-Security-Policy" scripts/ tests/ evaluator/ \
    | grep -viE "Content-Type|application/json"
scripts/verify_e2.py:133:    csp_lines = [ln for ln in conf.splitlines() if "Content-Security-Policy" in ln]
scripts/verify_deployed.py:244:        print("            docker compose build <service> && ...")
```

**This is not a parity bug**, which is why `verify_deployed` (19/19) is silent:

```
$ diff frontend/nginx.conf <(docker exec statesync-frontend-1 cat /etc/nginx/conf.d/default.conf)
(no output — identical)
```

The correct file is deployed. It just does not do what it says. Worth noting
beside it: `verify_deployed`'s frontend parity list is
`("frontend", "/usr/share/nginx/html", ["index.html", "app.js"])`, so
`nginx.conf` is outside every parity check in the project as well.

**The fix is one line repeated, and I verified it before proposing it:**

```
--- candidate fix, port 3092 (the four security add_headers repeated inside each location) ---
  /index.html  HTTP:200 CSP:1 XFO:1 XCTO:1 RP:1 CacheControl:1
  /app.js      HTTP:200 CSP:1 XFO:1 XCTO:1 RP:1 CacheControl:1
  /            HTTP:200 CSP:1 XFO:1 XCTO:1 RP:1 CacheControl:1
```

All three throwaway containers were destroyed (`docker rm -f csptest-old
csptest-new csptest-fixed`); no product container was touched.

**Bucket justification (§4.2).** `DEFECT`, and it cannot be a `TRADEOFF`: no
commit message or document written before this audit records a decision to stop
sending security headers. `56a23bf`'s message argues the opposite — it is a
commit *about* correcting what a browser actually receives. The open item
"F-V1 Class 4 … re-confirm Class 4 in an enforcing browser"
(`docs/open_items.md:13`) anticipates the *browser* not enforcing a CSP that is
sent; it does not contemplate no CSP being sent.

**Does not establish:** that any exploit exists. I found no injection sink —
cycle 003's citations card uses `textContent`, as the trace renderer does, and
M8 classes 1–3 pass. This is the removal of a defence-in-depth layer the
project claims to have, not a demonstrated vulnerability. It also does not
establish anything about `unsafe-inline`/`unsafe-eval` *within* the header
text, which remains correct in the file and would be correct if delivered; nor
have I checked whether any browser-based verification in
`docs/phase_e2_log.md` was run before `56a23bf` and would therefore have been
valid at the time.

### F-005-2 A fourth `phase_c2_v2` query cannot test what it was written to test, and the shipped model's pass on it is credited to SQL that answers a different question

**Rank: `PUBLISHABLE`. Bucket: `DEFECT`.**

The fixture discloses three queries that cannot fail (`c2g_03`, `c2g_10`,
`c2g_18` — all zero-row; audit 004 F-004-3). There is a fourth, by a different
mechanism, disclosed nowhere: **`c2g_15`'s WHERE clause matches every row in
the table.**

```
$ psql -U statesync_reader -d statesync -tA -c "..."
sellers total|30
display_name_local IS NULL|0
matches Devanagari regex|30
c2g_15 filter is a no-op?|YES - every seller matches
```

The question is *"Which sellers have a Devanagari display name recorded?"* On
this corpus the answer is "all of them", so the ground truth and a
filter-stripped query are the same result set:

```
$ psql ... -c "
WITH gt AS (SELECT seller_id, display_name, display_name_local FROM sellers WHERE display_name_local ~ '[Devanagari range]'),
     nofilter AS (SELECT seller_id, display_name, display_name_local FROM sellers)
SELECT 'rows only in ground truth', count(*) FROM (SELECT * FROM gt EXCEPT SELECT * FROM nofilter) a
UNION ALL SELECT 'rows only in no-filter', count(*) FROM (SELECT * FROM nofilter EXCEPT SELECT * FROM gt) b;"
rows only in ground truth|0
rows only in no-filter|0
```

The scorer, called directly, confirms the consequence:

```
$ python3 -c "from scorers import ExecutionAccuracyScorer; ..."
reference (c2g_15 ground truth, WITH the Devanagari filter): 30 rows
generated (filter OMITTED entirely):                        30 rows
scorer verdict: {'score': 1.0, 'match': True, 'generated_row_count': 30,
                 'reference_row_count': 30, 'row_recall': 1.0}
```

**This is not hypothetical — it is what the shipped 7B actually did**, in the
committed run behind the published 60.0%:

```
$ python3 -c "import json; d=json.load(open('docs/m4_diagnosis_v2fixture_7b.json')); ..."
published standard_ex: {'correct': 15, 'accuracy': 0.6, ...}  n: 25

c2g_15  standard_ex = True | strict_ex = True | category = correct
  question    : Which sellers have a Devanagari display name recorded?
  ground truth: ... WHERE display_name_local ~ '[ऀ-ॿ]' ORDER BY seller_id
  generated   : ... WHERE s.display_name_local IS NOT NULL LIMIT 1000;
  rows gen/ref: 30 / 30
```

`IS NOT NULL` is not a script test. The model answered *"which sellers have any
local display name"*, was scored `correct`, and that pass is one of the fifteen
that make `60.0%`. Two other models in the committed reports
(`m4_diagnosis_v2fixture_qwen14b_general.json` likewise `IS NOT NULL`) do the
same thing.

**Arithmetic consequence, stated conservatively.**

| basis | figure |
|---|---|
| published | 15/25 = **60.0%** |
| excluding the 3 disclosed unfailable queries (F-004-3) | 12/22 = **54.5%** |
| **also excluding `c2g_15`, whose pass is awarded to a non-answer** | **11/21 = 52.4%** |

**I checked the other fourteen passes for the same pattern and they are clean.**
Comparing each generated query against its ground truth, the differences are
alias names, `ORDER BY` and the harness's `LIMIT 1000` — no other predicate-level
divergence. The two that looked suspicious (`c2g_03`, `c2g_18`: generated SQL
with different projections and extra joins) are the already-known zero-row
cases, and they corroborate F-004-3 rather than extending it.

**The fixture's own note asserts the opposite of the data.**

```
$ python3 -c "...print(q['notes'])"   # c2g_15
display_name_local is nullable; only some seed rows populate it.
```

Zero of 30 are NULL. And the correction pass that produced this fixture could
not have caught it — `_audit.how_found` records that the second pass used
`scripts/attribute_failures.py`, *"which compares the TABLE SET of generated vs
reference SQL"*. `c2g_15` reads one table in both. A table-set comparison is
structurally blind to a predicate that is a no-op.

**Bucket justification (§4.2).** `DEFECT`, and specifically **not** a
`TRADEOFF`. The fixture's `_audit.known_remaining_weakness` is the only
pre-existing record of this family of problem and it names three queries:
*"c2g_03, c2g_10 and c2g_18 have ground truths returning ZERO rows."* `c2g_15`
is absent from it, from `docs/open_items.md`, and from `metrics-report.md`.
Nothing written before this audit shows anyone knew. A rationale for leaving it
would have to be constructed now, which §4.2 names as a defect wearing a
tradeoff's clothes.

**Note on what the right fix is.** The ground-truth SQL is *correct*; the
question is undiscriminating on this corpus. So this is not the F-004-3
judgment call in a new costume — that one asks whether to accept trivially
passable queries. This one has a cheap correct answer available (seed one
seller with a Latin-only `display_name_local`, or change the question), but
both touch a fixture or the corpus, and §4.3 plus the project's own "do not
tune against the fixture you report from" make that the owner's call, not mine.
**Disclosure is not the owner's call and is owed regardless.**

**Does not establish:** that the other 24 questions are well-posed. I read all
25 question/SQL pairs and executed all 25, but I only *proved* undiscriminating
-ness for `c2g_15`; a predicate that is a no-op on some subset of rows, or a
question with two defensible readings, would not necessarily show up in the way
this one did. It also does not establish that `52.4%` is the system's
capability — it is the same measurement with one more invalid pass removed, on
one model, on one corpus, at n=1. And it says nothing about `olist`/`olist_hard`,
where the real-data numbers live.
