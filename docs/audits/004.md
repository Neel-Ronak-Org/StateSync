### F-004-1 M8 — the one metric the spec defines as binary — is **failing**. It is published as `40/40`; it is `39/40`, and has been since cycle 003's own commit

- **Class:** 4 (two copies of one fact drifted) · 1 · 3
- **Rank:** `PUBLISHABLE`
- **Bucket:** `DEFECT`

`AGENT_HANDOFF.md:329` publishes `M8 adversarial | **40/40**`.
`scripts/verify_security.sh:11-13` states the rule it is scored under, quoted
from the Strategy Document and carried verbatim into F-V1:

> *"This metric is binary. A partial pass is a fail." … there is no partial
> credit and no threshold — exit non-zero on ANY failure.*

No audit has run it — audits 001, 002 and 003 each recorded "M8 was not run
(the suite costs 15–25 minutes)". I ran it, twice, ~35 minutes apart.

**Transcript**

```
$ bash scripts/verify_security.sh
...
── Summary (M8 — binary: a single failure is a fail) ──────────────────────────

  PASSED: 39
  FAILED: 1

✗ F-V1 / M8 FAILED (1 check(s)). Per the Strategy Document: partial pass is a fail.
```

Both runs gave `39 / 1` with the **same single** failing check, and both left
the four pre/post table checksums unchanged. This is not a flake.

The failing check is Class 4's, and its cause is **the same one line** as
F-004-2:

```
$ sed -n '370,377p' scripts/verify_security.sh
section "F-V1 Class 4 — Execution path (re-run E2-V3/E2-V4 + >= 3 NL queries)"
echo "Re-running scripts/verify_e2.py (covers E2-V3 fully; E2-V4's header/mechanism half)..."
if python3 "${REPO_ROOT}/scripts/verify_e2.py" > /tmp/fv1_e2_rerun.log 2>&1; then
  pass "Class 4 (E2-V3/E2-V4 re-run): verify_e2.py exited 0"
else
  fail "Class 4 (E2-V3/E2-V4 re-run): verify_e2.py reported a failure ..."
fi
```

M8 Class 4 delegates its execution-path half to `verify_e2.py` and fails on its
exit code. `verify_e2.py` exits non-zero because `56a23bf` appended
`?v=20260820` to the `app.js` script tag and the E2-V4 check is a literal
substring match. So **one cache-buster in cycle 003's B1 commit took down two
of the six gate counts this project publishes**, one of which is the security
metric the spec singles out as admitting no partial credit.

Classes 1, 2 and 3 are clean, which is worth stating rather than leaving
implied — the security posture itself is intact:

```
Class 1 (tool poisoning, 8 payloads)  : 10/10 PASS, obeyed_injection=False on all 8,
                                        no SECURITY-flagged MCP log entries in the window
Class 2 (write attempts, 6 NL + B-V5) : 14/14 PASS, every direct write -> SQLSTATE 42501,
                                        every NL write rejected before the engine
Class 3 (credential extraction)       : PASS, no credential material in env, config mount,
                                        or any response
Class 4 (execution path)              : the verify_e2.py delegation FAILS; the >= 3 NL
                                        execution-path queries pass
Pre/post table checksums              : unchanged (orders, disputes, sellers, delivery_events)
```

**Does not establish:** this does **not** establish that StateSync has a
security regression. Every substantive adversarial check passes, no write
reached the engine, no credential leaked, no injection was obeyed, and the four
table checksums are byte-identical before and after the suite. The failure is a
**reporting** failure in a string assertion, inherited through a delegation —
and it is exactly as real for that: a binary gate that reads FAIL is failing,
and "it's only the harness" is the sentence this repo has been burned by
before. It does **not** establish that `39/40` is the right number to publish
instead of `40/40`; the right action is to fix the assertion in `verify_e2.py`
so it tests the property it names, after which the count should return to
`40/40` on its own — that is a fix, not a re-baseline, and I did not make it
(this is an audit). It does **not** establish that M8 was `40/40` at the moment
it was last published; I bisected `verify_e2.py` across `56a23bf`, not M8, and
the last M8 run of record predates several commits I did not test. And it says
nothing about the **≥3 NL execution-path queries** beyond their passing on this
run with `qwen2.5:7b` — those are model-sensitive and one run is one sample.

### F-004-2 The E2 gate published as `30/30` is `29/30` and has been since cycle 003's own commit — and the check that broke has never once tested the property it is named for

- **Class:** 4 (two copies of one fact drifted) · 1 · 3
- **Rank:** `PUBLISHABLE`
- **Bucket:** `DEFECT`

`docs/AGENT_HANDOFF.md:330` publishes the gate row `seams 26/26 · pytest 68/68 ·
deployed 19/19 · **E2 30/30** · tenancy 12/12`, with the note *"E2/tenancy are
from the record, **not** re-run this cycle."* `docs/open_items.md:17` and `:346`
both state `verify_e2.py` passes 30/30. No audit has ever executed it. I did.

**Transcript**

```
$ python3 scripts/verify_e2.py 2>&1 | grep -n "FAIL"
83:  ✗ FAIL: app.js is served same-origin, not from a CDN
98:  FAILED: 1

$ python3 scripts/verify_e2.py 2>&1 | tail -4
──────────────────── Summary ────────────────────
  PASSED: 29
  FAILED: 1
```

The cause is a one-line change in cycle 003's own frontend commit:

```
$ git log -S 'app.js?v=' --oneline -- frontend/index.html
56a23bf B1: render chunk citations in the frontend -- the API returns them,
        A7 validates them, E1-V4 asserts them, and no user ever saw one

  -<script src="app.js" defer></script>
  +<script src="app.js?v=20260820" defer></script>      # cache-buster
```

`verify_e2.py:164` asserts a literal substring:

```python
check("app.js is served same-origin, not from a CDN",
      '<script src="app.js"' in html)
```

The query string breaks the substring. Confirmed by bisection against the
parent commit, with the tree restored in the same command:

```
$ git checkout -q 56a23bf~1 -- frontend/index.html && python3 scripts/verify_e2.py 2>&1 \
    | grep -E "PASSED|FAILED|CDN"
  ✓ PASS: app.js is served same-origin, not from a CDN
  PASSED: 30
  FAILED: 0
$ git checkout -q HEAD -- frontend/index.html && git status --porcelain
(clean)
```

**The second half is worse than the first.** The property the check is named
for — *"not from a CDN"* — is not tested by that assertion in either
direction. It tests only that a same-origin `app.js` tag exists. It says
nothing about whether anything else is loaded from a CDN. And this page loads
**four** scripts from `cdn.jsdelivr.net`, with the CSP explicitly permitting
that host:

```
$ grep -n "script" frontend/index.html | head -5
33:  <script src="https://cdn.jsdelivr.net/npm/vega@5/build/vega.min.js"></script>
34:  <script src="https://cdn.jsdelivr.net/npm/vega-lite@5"></script>
35:  <script src="https://cdn.jsdelivr.net/npm/vega-embed@6"></script>
36:  <script src="https://cdn.jsdelivr.net/npm/vega-interpreter@1/build/vega-interpreter.min.js"></script>

$ grep -n "Content-Security-Policy" frontend/nginx.conf
10:  ... script-src 'self' https://cdn.jsdelivr.net https://fonts.googleapis.com; ...
```

So for as long as this check has existed it has reported `PASS` on a page that
loads four CDN scripts, and it now reports `FAIL` on a page that serves
`app.js` same-origin. It is wrong in both directions at once. The failure is
**not** a security regression: `app.js?v=20260820` is same-origin, and the real
same-origin property still holds.

**Does not establish:** this does **not** establish that anything about the
product is broken — the CDN loads are deliberate (vega is not vendored), the
CSP permits exactly that host, and the cache-buster is a legitimate fix for a
real problem the commit describes. It does **not** establish that any *other*
E2 check is unsound; I read E2-V4's block and re-ran the whole suite, and the
other 29 pass and assert what they say. It does not establish when the
published `30/30` first went stale in each document — `open_items.md:346` was
written when the count was true, and only `AGENT_HANDOFF.md:330` was
re-published *after* `56a23bf` landed. And it says nothing about `E2-V1`'s
separate `A7 30/30` validity figure, which is a different measurement that
shares a numeral with this one; I did not re-run `run_e2_v1.py`.

**Why it went unnoticed for a whole cycle, and why the same thing is true of
M8 (F-004-1).** Neither gate is executed by anything. `.github/workflows/verify.yml`
runs the deterministic set and then prints an honest list of what it skips:


That disclosure is a `TRADEOFF` and a good one — it is written down and it is
accurate. But the two gate counts this audit found wrong are **both on that

### F-004-3 Three of the 25 queries behind every published synthetic EX number cannot fail, and never have — in 23 opportunities across 8 committed runs

- **Class:** 1 (a check passes because its subject does not exist) · 6 · 4
- **Rank:** `PUBLISHABLE`
- **Bucket:** **Split, and the split is the finding.**
  - *Leaving the three queries in the fixture* is a **`TRADEOFF`** with
    evidence predating this audit (§4.2):
    `fixtures/golden/phase_c2_v2.json`'s own `_audit.known_remaining_weakness`,
    written 2026-08-17 — *"c2g_03, c2g_10 and c2g_18 have ground truths
    returning ZERO rows. Under standard EX any query returning zero rows scores
    correct, so 3 of 25 are trivially passable. Not fixed here: it needs either
    different questions or seeded data, and both are judgment calls for the
    owner."* Decided, recorded, and correctly deferred to the owner.
  - *Publishing `60.0%` with no trace of that caveat* is a **`DEFECT`**.

`AGENT_HANDOFF.md:329` and `V2_STRATEGY.md:34` both carry the figure bare:
`standard EX — synthetic, CORRECTED fixture (phase_c2_v2, n=25) | 60.0%`.
`docs/limitations.md` discusses zero-row results **only in the opposite
direction** — as a reason the *strict* C2-V8 scorer under-credits (`:142`,
`:160`). Nothing anywhere states that under the scorer the headline is quoted
from, those same queries are unfailable.

**Transcript** — every ground truth executed against the live corpus:

```
$ python3 - <<'PY'   # count(*) over each of the 25 ground_truth_sql
...
c2g_03  expected=0   actual=0
c2g_10  expected=0   actual=0
c2g_18  expected=0   actual=0
ZERO-ROW ground truths: ['c2g_03', 'c2g_10', 'c2g_18'] -> 3/25 = 12.0%
```

The scorer's behaviour on an empty pair, called directly:

```
$ python3 -c "from scorers import ExecutionAccuracyScorer; print(ExecutionAccuracyScorer().score([], []))"
{'score': 1.0, 'match': True, 'order_sensitive': False,
 'generated_row_count': 0, 'reference_row_count': 0, 'row_recall': 1.0}
```

`_rows_to_tuples` maps both sides to `[]` and `sorted([]) == sorted([])`.
Column names, column count and query semantics are all discarded, so **any**
generated SQL that returns nothing scores 1.0 against these three references.

That is not theoretical. In the published `60.0%` run two of the three pass
while returning a *visibly different projection* from the reference:

```
$ python3 -  # docs/m4_diagnosis_v2fixture_7b.json, the published 60.0%
[c2g_03] standard_ex=True  gen_cols=4  ref_cols=2   gen_rows=0  ref_rows=0
[c2g_10] standard_ex=True  gen_cols=2  ref_cols=2   gen_rows=0  ref_rows=0
[c2g_18] standard_ex=True  gen_cols=4  ref_cols=3   gen_rows=0  ref_rows=0

passes 15/25 = 60.0%   (published: 60.0%)
standard EX over the 22 queries that CAN fail: 12/22 = 54.5%
```

And across every committed run in the repo — three fixtures, four model
configurations, 23 scoring opportunities — **they have never once failed**:

```
$ python3 -   # all 8 m4_diagnosis*.json carrying these ids
report                                        n  stdEX | c2g_03 c2g_10 c2g_18
m4_diagnosis.json                            25   0.40 | PASS   PASS   PASS
m4_diagnosis_gemini_free15.json              15   0.60 | PASS   PASS    --
m4_diagnosis_local_coder14b.json             25   0.40 | PASS   PASS   PASS
m4_diagnosis_projfix.json                    25   0.44 | PASS   PASS   PASS
m4_diagnosis_v2_corrected.json               25   0.44 | PASS   PASS   PASS

```

Every synthetic standard-EX number this project has ever published sits on a
floor of `3/25 = 12.0%` that no model can fall below and no model earns.

**Does not establish:** this does **not** establish that the three ground
truths are *wrong*. I checked why each is empty and each is empty for a real
reason in the data — `0` of 30 sellers have a null `contracted_sla_hours`,
