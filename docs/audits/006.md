### F-006-1 The evidence that the chunker finally chunks is 70% the work of the fallback that exists because it doesn't

`PUBLISHABLE` · `DEFECT`

**The claim.** Audit 004's F-004-6 was that `_chunk_words` had never once split
a document — every "chunk" in the project was a whole document, so every M6
number was measured in a regime nobody had acknowledged. Cycle 005 set out to
close that, and published the closure in two places:

`docs/limitations.md`:

> `_chunk_words` had never split a document before this cycle (F-004-6). It now
> has: **1,072 of the 2,567 review documents produced more than one chunk**, the
> largest producing 294.

`docs/AGENT_HANDOFF.md` §7 carries the same figure:

> **1,072 of them produced more than one chunk, the largest 294, so the chunker
> split a document for the first time in this project's history.**

**There are four numbers for this quantity and no two of them agree.**

The generator's own committed docstring (`scripts/gen_olist_review_digests.py`,
`f5077c6`, the only commit the file has ever had):

```
$ sed -n '9,18p' scripts/gen_olist_review_digests.py
WHY A DIGEST, NOT A RAW-ROW INGEST. Measured during audit 005: 41,746
commented reviews average 11.9 words (max 45) against this project's
512-token chunk target (`config/statesync.toml [retrieval]`), so a raw
ingest leaves `_chunk_words` exactly as unexercised as F-004-6 found it --
every chunk would still be a whole "document." Grouped per seller instead,
2,567 sellers have >= 1 commented review, median digest length 56 words,
max 12,426, and 246 exceed the 512-word chunk target -- so the real
`scripts/ingest.py` chunker splits a document for the first time in this
project's history
```

Run that same generator today, against the unchanged `olist` schema, and it
does not reproduce its own docstring:

```
$ python3 scripts/gen_olist_review_digests.py --out $SCRATCH/manifest_audit006.json
Sellers with >= 1 commented review: 2567
Total commented reviews: 42007
Digest word count: median 77, max 15857
Digests exceeding the 512-word chunk target: 313
Wrote .../manifest_audit006.json (2567 documents)
```

`median 56 → 77`, `max 12,426 → 15,857`, `246 → 313`. This is **not**
non-determinism — two runs today are byte-identical to each other and to the
committed manifest (§ "re-confirmed", and the transcript under F-006-3). **Why
the docstring disagrees cannot be recovered**: the file has exactly one commit
(`git log --follow` → `f5077c6` alone), so the pre-`DISTINCT ON`-fix query it
may have been measured against is not in history. What is verifiable is that
the committed code does not reproduce its own committed docstring against the
unchanged corpus, and that the *database* agrees with the code, not the
docstring — so the docstring is the wrong copy, not the corpus.
(`41,746` vs `42,007` is a separate, benign name collision: `41,746` is the
count of distinct commented reviews, `42,007` is the seller×review pairs the
generator's `JOIN olist.order_items` produces, and the script prints the second
under the first's label.)

**Now separate the two mechanisms.** `_chunk_words(text, 512, 64)` splits a
document only if it exceeds 512 words. `_embed_allowing_split` is a *different*
thing added in the same cycle: when Ollama rejects a chunk for exceeding
`mxbai-embed-large`'s real 512-**token** context, it halves that chunk by word
count and retries, recursively, up to depth 4. Its docstring is explicit about
which of the two is supposed to be doing the work:

```
$ sed -n '135,140p' scripts/ingest.py
    This is a safety net around the real chunker, not a second one: chunk
    boundaries from `_chunk_words` are unchanged for every chunk that already
    fits, which is the overwhelming majority (see the outcome section for the
    measured split-event count).
```

Joining the manifest's per-document word counts to the persisted chunk counts
separates them exactly:

```
$ python3 - <<'PY'   # manifest word counts ⋈ database chunk counts
DB review documents: 2567  total chunks: 13125
DB documents with >1 chunk        : 1054
Documents >512 words (chunker WILL split): 313
multi-chunk AND >512  (real chunker splits): 313
multi-chunk BUT <=512 (fallback-only splits): 741
>512 but single chunk in DB        : 0
document_id set mismatch manifest vs DB: 0
PY
```

- **313** documents are what `_chunk_words` actually splits.
- **741** — 70% of the published population — are documents *under* the 512-word
  target that `_chunk_words` emitted as a single chunk, and that only became
  multiple chunks because the embedding call rejected them.
- **1,054**, not 1,072, is what the database holds. The published figure does
  not reproduce against the corpus it describes.

**And the fallback is not the exception its docstring claims — it is the rule.**
If "the overwhelming majority" of chunks kept `_chunk_words`' boundaries, the
corpus would contain chunks at or near 512 words. It contains none:

```
$ psql -U statesync_reader -d statesync -tA -c "
    SELECT min(...), round(avg(...)), max(...) FROM document_chunks c
    JOIN documents d USING (document_id) WHERE d.doc_type='review_digest';"
14|69|154
```

Minimum 14 words, mean 69, **maximum 154** — against a `chunk_target_tokens`
of 512. Every chunk `_chunk_words` emitted at its target size was rejected and
halved at least twice. For contrast, the baseline corpus F-004-6 was written
about runs 19–95 words per chunk:

```
policy|8|31|68     sla_annexure|8|53|60     sop|8|19|67     supplier_agreement|12|54|95
```

So the regime F-004-6 identified — *a chunk is a small whole passage, and the
512-token path is unexercised* — **is still the regime the corpus is in.** It
was narrowed from "every chunk is a whole document" to "every chunk is a
69-word fragment", which is a real change and a real exercise of the split
path for 313 documents. It is not the change the published number describes.

**Bucket: DEFECT, not TRADEOFF.** §4.2 requires a tradeoff's justification to
predate the audit. `limitations.md` is candid about what the fallback did not
get (*"neither has a quality measurement — only 'it eventually embedded
successfully' is verified"*) and states the fallback's own chunk count
(`2,119`) in the same paragraph — but it attributes the `1,072` to
`_chunk_words` in the sentence that closes F-004-6, and nothing anywhere
separates the 313 from the 741. There is no pre-existing document in which
this distinction is drawn and set aside.

**Does not establish.** This does not establish that any M6 figure is wrong,
that the corpus is badly chunked *for retrieval* (F-006-2 addresses retrieval
on its own evidence), or that `_embed_allowing_split` was the wrong response to
the context-length failure — it was a reasonable one, caught live, and it
works. It establishes only that the number published as the measure of
`_chunk_words`' first real exercise is 3.4× that quantity, does not reproduce
against the database, and is contradicted by the generator's own docstring in
a third direction.

### F-006-2 The 2,567-document review corpus is retrievable but not addressable

`PUBLISHABLE` · `DEFECT`

**What cycle 005 measured, and the gap it recorded.** The ingest was measured
for *interference*: does adding 13,125 chunks move the existing 16-query
`phase_e1.json` scores? Answer: not at all, at the per-chunk-ID level.
`docs/limitations.md` states the residual honestly, before this audit:

> It does **not** establish that retrieval is robust to scale in general, **that
> a review-adjacent English query would retrieve correctly**, or that the
> chunker's now-exercised split path produces chunks of good retrieval quality
> — none of that was measured.

**First, the good news, because it is load-bearing.** A null interference result
has two explanations: the corpora sit far apart in embedding space, or the review
chunks are not retrievable by anything. Cycle 005 asserted the first and did not
exclude the second. It is excluded. Embedding a review-topical question with the
shipped `mxbai-embed-large` and running `semantic_search`'s exact SQL:

```
$ # query: "What do customers say about seller 0015a82c2db000af6aaaf3ae2ecb0532?"
$ psql … -c "SELECT d.doc_type, dc.chunk_id, round((1-(dc.embedding <=> :qvec))::numeric,4)
             FROM document_chunks dc JOIN documents d USING (document_id)
             WHERE dc.tenant_id='t_capstone_default'
             ORDER BY dc.embedding <=> :qvec LIMIT 8;"
review_digest|doc_review_digest_ad8ada0ffa993cb1197d102d9ab21a3e_c000|0.8071
review_digest|doc_review_digest_e72b4feb7abe210c52aa667abc25a3a2_c000|0.8021
review_digest|doc_review_digest_67225bff54a172ff67579aaf583efd78_c000|0.7984
review_digest|doc_review_digest_8fbd63429be6d3e5e6d1a709b6464802_c000|0.7971
review_digest|doc_review_digest_e5d4b2b0c3bca22085f7a19a28de0c42_c000|0.7951
review_digest|doc_review_digest_c9d2ba8dde44a275ae06475ed1d2fafc_c000|0.7949
review_digest|doc_review_digest_23ff42c4bf1f8f16cddb19d8b972974a_c000|0.7944
review_digest|doc_review_digest_70c4eedec9cb4a85cda2f3f9673557b4_c000|0.7906
```

Review chunks are retrievable, and they dominate the top-8. **Cycle 005's
reading of its own null result survives the test it said it had not run.**

**Now the defect. Every one of those eight is the wrong seller.** The query
names `0015a82c2db000af6aaaf3ae2ecb0532` verbatim. That seller's own digest:

```
$ psql … -c "WITH ranked AS (SELECT chunk_id, document_id,
      row_number() OVER (ORDER BY embedding <=> :qvec) AS rnk,
      round((1-(embedding <=> :qvec))::numeric,4) AS score
      FROM document_chunks WHERE tenant_id='t_capstone_default')
   SELECT rnk, score, chunk_id FROM ranked
   WHERE document_id='doc_review_digest_0015a82c2db000af6aaaf3ae2ecb0532';"
2365|0.6603|doc_review_digest_0015a82c2db000af6aaaf3ae2ecb0532_c000
```

**Rank 2,365 of 13,161, against `semantic_top_k = 8`.** Off by a factor of
~300. And 0.6603 is barely above the corpus-wide median for this same query:

```
$ psql … -c "SELECT max(...), percentile_cont(0.99)…, percentile_cont(0.50)…, min(…)"
best 0.8071 | p99 0.7402 | median 0.6026 | worst 0.3349
```

The exact 32-hex seller id contributes essentially nothing to the ranking.

**The mechanism, measured.** Each digest is one document per seller, chunked; the
seller id appears **once**, in the `# Customer reviews — seller <id>` header of
chunk `c000`. Everything after that is undifferentiated Portuguese review text:

```
$ psql … -c "SELECT CASE WHEN c.ordinal=0 THEN 'first' ELSE 'continuation' END,
             count(*) FROM document_chunks c JOIN documents d USING (document_id)
             WHERE d.doc_type='review_digest' GROUP BY 1;"
continuation (ordinal>0)|10558
first (ordinal=0)|2567

$ psql … -c "SELECT count(*) FILTER (WHERE position(
               replace(d.document_id,'doc_review_digest_','') IN c.content_md) > 0)
             AS contains_seller_id, count(*) AS continuation_chunks
             FROM document_chunks c JOIN documents d USING (document_id)
             WHERE d.doc_type='review_digest' AND c.ordinal > 0;"
0|10558
```

**Zero of 10,558 continuation chunks contain their own seller id** — 80.4% of the
corpus. A retrieved continuation chunk cannot be attributed to a seller from its
text at all. And the split boundaries are not clean:

```
$ psql … -c "SELECT count(*) FILTER (WHERE content_md LIKE 'Review %') AS at_boundary,
             count(*) FILTER (WHERE content_md NOT LIKE 'Review %') AS mid_review, count(*)
```

### F-006-4 Five of the 34 real-data questions state a restriction the data makes invisible

### F-006-5 The hard fixture is softer than its labels on two of 16

Exactly one table chunk and one narrative chunk each — which is *why* F-004-6

**The figure therefore decomposes exactly, and my `1,054` was the same number
minus these 18:**

| | documents | split by |
|---|---|---|
| baseline corpus | **18** | `_extract_document_chunks`' table/narrative separation — **before this cycle, and F-004-6's own subject** |
| review digests ≤512 words | **741** | `_embed_allowing_split`, the context-length fallback |
| review digests >512 words | **313** | **`_chunk_words` — the only ones that support the claim** |
| published as evidence the chunker chunks | **1,072** | |

So the sentence *"`_chunk_words` had never split a document before this cycle.
It now has: 1,072 of the 2,567 review documents produced more than one chunk"*
is wrong three ways in one line: the denominator is 2,585 not 2,567; 741 of the
numerator is the fallback's work; and **18 of the numerator are the very
documents whose multi-chunk-ness is the counter-example — they were multi-chunk
before the cycle and are not `_chunk_words` splits at all.**

**The frozen criterion did not require the wrong number — it permitted it.**
C4 reads *"at least one ingested document produces more than one chunk, and the
outcome records how many documents did."* When it was frozen,
`_embed_allowing_split` did not exist; "produced more than one chunk"
unambiguously meant `_chunk_words`. The fallback was added mid-build, and its
arrival **silently changed what the criterion measured** without changing a
word of it. Nothing in the protocol catches that: §4.4 protects the criteria
text from moving, and here the text never moved — the world underneath it did.
That is a §7 gap worth writing down, and it is the most transferable thing in
this audit.

**Does not establish.** This does not establish that C4 was unmet — 313 > 0, so
the chunker did split documents for the first time, and cycle 005's headline
claim is true. It does not establish that anyone knew: the count was taken
honestly and stated as what it was (*"1,072 documents with >1 chunk"* — over the
table, which is literally correct); the error is in the prose that later
attributed it to 2,567 review documents and to `_chunk_words`. It does not
establish that the 18 baseline documents' two-chunk structure is wrong — it is
correct and intended. And it does not re-measure `2,119`, the fallback's own
chunk-level count, which I read but did not verify.
