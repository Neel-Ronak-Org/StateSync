### F-001-1 The flag whose wrong value already faked a measurement is in neither the guard nor the provenance record

- **Class:** 9 (contaminated measurement) · 10 (unchecked claim)
- **Rank:** `PUBLISHABLE`
- **Bucket:** `DEFECT`

Setting it wrong is precisely what produced `80d35c8` — the agent answering
from 550 synthetic rows while being scored against 99,441 real ones. That

like an ordinary bad run".

### F-001-5 `row_recall` — offered as the honest counterweight to value recall — carries the same de-duplication defect

- **Class:** 2 (a metric measures something other than its name)
- **Rank:** `BACKLOG`
- **Bucket:** `DEFECT`

`AGENT_HANDOFF.md` §6 flags mean value recall as weak *because* it is
"unaligned and de-duplicated", and offers row recall as the sound alternative:
"Mean **row** recall is **48%**". That number comes from
`ExecutionAccuracyScorer.row_recall`, which de-duplicates too — and does so in
the same class whose neighbouring line argues that duplicates are meaningful:

```python
# match  (the pass/fail decision) -- MULTISET
match = sorted(gen) == sorted(ref)
    # "Multiset comparison: duplicate rows are meaningful in SQL results,
    #  so sorted() rather than set()."

# row_recall (the reported metric) -- SET
"row_recall": len(set(ref) & set(gen)) / len(set(ref))
```

**Transcript** — whether it is currently inflating anything, measured rather
than assumed:

```
$ python3 -c "
import json
for f in ['docs/m4_diagnosis_olist_local7b.json','docs/m4_diagnosis_olist_gemini.json','docs/m4_diagnosis_v2fixture_7b.json']:
    d=json.load(open(f))
    dup=sum(1 for r in d['results']
            if len([tuple(str(v) for v in row.values()) for row in r['reference_rows']])
             != len({tuple(str(v) for v in row.values()) for row in r['reference_rows']}))
    print(f.split('/')[-1], 'refs with duplicate rows:', dup, 'of', len(d['results']))"
m4_diagnosis_olist_local7b.json  refs with duplicate rows: 0 of 18
m4_diagnosis_olist_gemini.json   refs with duplicate rows: 0 of 18
m4_diagnosis_v2fixture_7b.json   refs with duplicate rows: 0 of 25
```

Zero of 61. Every reference is a `GROUP BY` or a scalar, so no published
`mean_row_recall` is inflated. `BACKLOG` for that reason and no other.

**Does not establish:** this does **not** show 48% is wrong — on these three
fixtures set and multiset agree exactly, so the figure stands as published. It
covers three reports, not the full `docs/*.json` set. And it says nothing about
fixtures v2 has not written yet: B2's hard fixture is specified as window
functions and correlated subqueries, which is the query shape most likely to
produce genuinely duplicated result rows, so this becomes live precisely when
that fixture lands.
