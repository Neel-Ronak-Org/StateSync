Date: 2026-08-15. Builds on Phase E1 (`0f0ebb9`) and the Anthropic-gap packet

## Scope

This log covers **only the model-independent half of E2** — the deterministic,
binary-verifiable deliverables: A7 dual validation, CSP-safe rendering, the M7
scorer machinery, and the malicious-spec rejection suite. It corresponds to
Tasks 6–9 of `docs/AGENT_TASKS_phase_e_gap.md`.

**Not covered, deliberately (Task 10):** E2-V1's M7 chart-*quality* score on
real generated charts, and anything else whose pass condition depends on
generation quality. The Synthesizer still emits `chart: null` on every route —
teaching it to populate `chart` is the model-dependent half of E2 Deliverable 1
and is not part of this work. The scorer, the fixture, and both validators are
in place and tested, so that half is a Synthesizer prompt change plus a
measurement run, not new machinery.

Any M7 number produced before then is a **local-model figure pending the graded
re-baseline** (`docs/rebaseline_runbook.md`), per Strategy §7.0 and BD6.

## Bugs found and fixed

1. **The orchestrator validated a different object than it emitted.** A7
   requires validation "in the orchestrator before the response leaves the
   process". `synthesizer_node` validated its own output, but `main.py` then
   rebuilt the response — recomputing citations from `final_state` (necessary,
   per the E1 scratch-key finding) and passing `final_state.vega_spec` straight
   through. Nothing re-checked the assembled payload. With `chart` always null
   in E1 this was invisible; the moment E2 populates `chart` it would have been
   an unvalidated response. Fixed by validating at the boundary in `main.py`.
2. **The frontend had no A7 validation whatsoever.** `renderChart` rendered
   `data.chart` directly. The "two independent validations" guarantee was
   one validation. This is the single largest gap E2 closes.
3. **A7's `transform` escape hatch left ms_05 accepted.** A7 declares
   `transform` items `additionalProperties: true`, so a `calculate` transform
   satisfies the literal schema — the orchestrator rejected 9/10, not 10/10,
   while E2-V3 requires 10/10. Resolved as **BD7**: a separately-named
   expression audit alongside the schema, rather than editing A7's declared
   shape in either direction.
4. **`oneOf` collapsed every chart rejection into one generic message.**
   jsonschema reported "is not valid under any of the given schemas" with the
   whole spec embedded, so the worked example's three grounds only *appeared*
   present because the dump contained the words. E2-V3 explicitly calls this
   out: "a single generic rejection means the other two paths are untested."
   Fixed by expanding `oneOf`/`anyOf` sub-errors and dropping the trivial
   "not of type 'null'" branch, so each ground is reported at its own path.
5. **Three separate frontend rendering faults, none of which would have
   surfaced without actually rendering in a browser.** All found by testing,
   not by reading:
   - `vega@5/build/vega-interpreter.min.js` **404s** — the interpreter was
     never loading. The package is `vega-interpreter@1`.
   - `vega` core was **never loaded at all**; the page had only vega-lite and
     vega-embed, and vega-embed bundles neither. Every render threw
     `e.isString is not a function` before reaching any CSP consideration.
   - `vega-core.min.js` is **not standalone** — it omits bundled d3
     dependencies, throws on load, and leaves `window.vega` an empty object.
     The full `vega@5` build is the correct one.
   - The interpreter probe selected `window.expressionInterpreter`, a **decoy**:
     a bare function with no `.operator`, which throws
     `this.expr.operator is not a function` on every render. The usable object
     is `vega.expressionInterpreter` (`{operator, parameter, event, handler,
     encode}`). The probe now checks *shape*, not truthiness.

   The pre-existing code carried a comment asserting it used "vega-interpreter
   … NOT the default expression compiler". It was not using either: nothing
   rendered at all. The comment was aspirational, and E2-V4 is what caught it.

## Notes on scope decisions

- **Reference specs are authored, not observed.** `gen_phase_e2_fixture.py`
  makes no live calls. Deriving reference specs from a running system would
  freeze whatever the model happened to emit and score it against itself, which
  is the circularity E2-V1 exists to avoid.
- **`data.values` is not scored.** Appendix 1's three weights sum to 1.0 over
  exactly mark / encoding / transform. Scoring `data`, `title`, `sort`, `width`
  or `height` would mean inventing a fourth component the spec does not define
  (A0.1). Stylistic properties are simply outside the scored set, which is also
  what makes an "extra `title`" cost nothing while an extra *channel* costs
  precision — M7's own "unexpected colour" case.
- **The `Scorer` seam is built here rather than in Part F.** A8 assigns it to F,
  but E2 Deliverable 8 needs the scorer now, and A0.5 forbids deferring a seam
  past the phase whose consumer exists. Part F adds the gated vision scorer
  (D11) with a `register_scorer()` call and a config edit; no dispatch site
  changes.

## Task 10 — chart emission built, and E2-V1 run for the first time

Until now the Synthesizer emitted `chart: null` on every route, so E2-V1's M7
was not "deferred pending a better model" — there was **nothing to score**.
Task 10 closes E2 Deliverable 1.

### Design: the model picks the shape, the code supplies the data

`build_chart()` takes the model's proposed `{mark, encoding, title}` and
attaches `data.values` from the real SQL rows in code. The model is never
asked for, and never trusted with, the data itself.

This is not a stylistic preference. A model that emits its own `data.values`
can produce a chart that is fully A7-valid — every number well-formed — and
that silently contradicts the prose answer above it. Generating the data in
code makes that class of error *impossible* rather than merely unlikely, which
is what Strategy §1's "grounded in real rows" has to mean if it means anything.

Guards, all of which return `None` rather than a repaired spec (A7: "It never
returns a repaired chart"):
- `mark` not in the A7 enum → drop the chart.
- an encoding channel naming a column absent from the result → drop the
  channel (Vega-Lite renders an unknown field as a silently empty channel).
- non-A7 encoding properties → stripped.
- `is_chartable()` gate: below `chart_min_rows`/`chart_min_columns` a result is
  an answer, not a chart.

### The 8 nulls were investigated rather than attributed to the model

All 30 fixture queries expect a chart, so each null scores 0.0 and the null
count — not spec quality — was doing most of the damage to the mean. The
obvious reading ("a 7B model just isn't good at charts") turned out to be
wrong for most of them.

Diagnosis found **a real code defect, not a model ceiling**: the Synthesizer
was returning a perfectly good JSON object whose `answer_text` contained
*literal* newlines instead of the `\n` escape JSON requires. That is invalid
JSON by the letter of the spec, `json.loads` rejected it, and the entire
structured response — chart included — was discarded into the plain-text
fallback. It affected result sets that had already passed the chartability
gate: 10 rows × 2 columns, 32 rows × 5 columns.

The bug had been *logging itself the whole time* and saying nothing useful:
`"Synthesizer returned non-JSON for query_id=..."` recorded that parsing
failed while throwing away **what** failed. Adding the response preview to
that warning identified the cause immediately. This is the same defect class
as the evaluator's empty-string error strings — a log that cannot diagnose its
own event.

Three fixes:
1. `json.loads(..., strict=False)` — permits control characters inside string
   values. Nothing else is relaxed; a genuinely malformed object still raises
   and still falls through to plain text.
2. `_extract_json_object()` — recovers an object embedded in surrounding prose
   via a string-aware brace scan (braces inside string values and escaped
   quotes do not affect depth). Returns `None` rather than anything partial.
3. The non-JSON warning now logs a truncated response preview.

Verified: a 10-row × 2-column result that produced `chart: null` before the
fix produces a real `bar` chart after it.

**Residual nulls are genuine and are not papered over.** After the fix the
remaining ones split into three honest categories:
- **upstream SQL returned 0 rows** (e.g. "Scatter of promised versus actual
  delivery hours") — an M4-class text-to-SQL failure, not a charting failure;
- **SQL returned 1 wide row** (e.g. "What share of orders is B2B versus B2C?"
  → one row, two count columns) where the reference expects an `arc` over a
  long-format two-row result. Correctly gated out by `is_chartable`; the
  mismatch is in the SQL's shape, upstream of the chart;
- **the model chose `null`** on un-aggregated raw rows (32 dispute rows with
  `narrative`), where a bar chart would have needed a count aggregate. That
  one is a real model-quality limitation (BD6).

### Correction — the JSON fix recovered 1 of the 8 nulls, not 7

The entry above claimed the JSON parse defect "accounted for 7 of the 8
chart:null results". **That was wrong, and the correction is recorded rather
than edited away.** It was an extrapolation from two probe queries that showed
the parse failure, generalised to the whole null set without measuring it. The
re-run measured it:

| | pre-fix | post-fix |
|---|---|---|
| A7-valid | 30/30 | **30/30** |
| `chart:null` | 8 | **7** |
| M7 mean spec score | 0.4592 | **0.4850** |

Null set difference: `e2_008` recovered; nothing regressed; the other seven
were null in both runs. The parse defect was real and is genuinely fixed —
`e2_008` is the proof — but it was **one** of the eight, not seven.

**Full measured accounting of the 8 original nulls**, by row/column shape of
the SQL that fed them:

| Cause | Count | Queries | Nature |
|---|---|---|---|
| SQL returned **0 rows** | 4 | `e2_009`, `e2_010`, `e2_015`, `e2_022` | upstream text-to-SQL failure (M4 class), not a charting failure |
| SQL returned **1 wide row** | 1 | `e2_007` | `is_chartable` correctly gates it; the reference expects an `arc` over a long-format result, so the shape mismatch is upstream |
| **Model declined** despite good data | 2 | `e2_017` (32×5), `e2_030` (360×3) | genuine model-quality limitation (BD6) |
| **JSON parse defect** | 1 | `e2_008` (10×2) | real code defect, fixed |

**The conclusion that matters, and it is not the one the number suggests:**
**M7 on the local model is dominated by upstream SQL quality, not by charting
quality.** Five of eight nulls exist because the SQL returned nothing or the
wrong shape — the chart layer never got a chance. That is consistent with M4
sitting at 28–36% on this model, and it means M7's local figure should be read
as *partly a downstream reflection of M4* rather than as a clean measure of
the Synthesizer's chart competence. Over the 23 charts actually produced the
mean is 0.633.

This is exactly why E2-V1 requires the `chart:null` count to be reported
separately instead of averaged into the mean — the two move for unrelated
reasons, and collapsing them would have hidden a text-to-SQL problem inside a
charting metric.
